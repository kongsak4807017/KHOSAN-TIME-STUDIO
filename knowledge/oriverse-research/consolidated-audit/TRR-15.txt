143 — Pathfinding, Steering และ Avoidance ใช้ Algorithm ใด?
1. Direct Answer: คู่มือระบุว่า TileGrid Pathfinding ใช้ A* บน Tile Coordinates และมี Flow Fields สำหรับกลุ่มที่มีเป้าหมายร่วมกัน แต่ไม่ได้เปิดเผย Algorithm ภายในของ Crowd Avoidance เช่น ORCA/RVO หรือ Steering Optimization Method
2. Architecture: ระบบแบ่ง Global Route Planning กับ Local Avoidance ชัดเจน: TileGrid สร้าง Path หรือ Flow Field ส่วน Crowd Movement แปลง Route เป็น Preferred Velocity แล้วระบบ Avoidance ปรับการเคลื่อนที่
3. Source Evidence: tile_pathfinding, object_types
4. API Contract:
TileGridFindPath8 คืน Path แบบกลับลำดับ Goal → Start และ Path Lists เก็บ Tile IDs ที่เป็น Opaque Numbers
5. Working Example: คู่มือรองรับการสร้าง TileGrid เดียวใน Manager แล้วให้ NPC หลายตัวใช้ Shared Grid และ Shared Flow Field เดียวกัน ไม่ควรสร้าง Navigation Grid ใหม่ทุก NPC
6. Execution Trace — Expected: Build Grid → Define Walkability → Find Path/Build Flow → Submit Movement → Avoidance Resolution → Update NPC Position
7. Limits & Failure Modes: Dense TileGrid สูงสุด 1,048,576 Tiles; Terrain-based Grids รองรับ 8,192 Tiles ต่อแกน แต่การหา Path ระยะไกลบางประเภทจำกัด 256 Tiles และต้องใช้ TileGridFindRoute แทนสำหรับเส้นทางไกล
TileGridBakeCrowdObstacles เป็น Snapshot จึงต้อง Re-bake เมื่อ Walkability เปลี่ยน
8. Verification: Expected: NPC เดินอ้อมอาคารได้เมื่อมี Grid ถูกต้อง; Actual: Not Run
9. Disclosure Status: A* / Flow Fields Documented; Avoidance Solver Internals Undisclosed
10. Research Gaps: A* Heuristic, Tie-breaking, ORCA/RVO Usage, Avoidance Solver Complexity, Dynamic Obstacle Handling และ Determinism at High Density

145 — รองรับ Animation Blending, State Machines และ IK หรือไม่?
1. Direct Answer: Oriverse รองรับ Animation Blending และ Procedural Bone Overrides ที่เปิดเผยผ่าน API โดยเฉพาะ Upper-body Animation Layer และ Bone Look-at แต่ยังไม่พบ Public Contract สำหรับ Animation State Machine Graph Editor หรือ Full-body IK Solver ที่สามารถระบุ Algorithm ได้
2. Architecture: ระบบมี Base Clip สำหรับการเคลื่อนไหวหลัก เช่น Walk/Run และสามารถซ้อน Upper-body Clip หรือ Bone-level Transform เพิ่มเติม ขณะที่ Auto Locomotion เลือก Clips ตามสถานะการเคลื่อนที่ ส่วน FSM ระดับ Gameplay สามารถเขียนเองด้วยตัวแปร State ของ Weave
3. Source Evidence: weave_coding → animations; Built-in Function Declarations ของ PlayUpperBodyAnimation, SetUpperBodyAnimationWeight, SetBoneRotationMix และ BoneLookAt
4. API Contract:
SetBoneRotationMix เป็น Display-only Bone Layer จำกัด 16 Bones ต่อ Object ส่วน BoneLookAt ทำให้ Bone เล็งไปยัง World Target ภายในขอบเขตมุมที่กำหนด
5. Working Example — จากรูปแบบในคู่มือ:
ต้องมี Friend เป็น Reference ที่มีอยู่และใช้ Rig ที่มีกระดูกตามชื่อ จึงยังไม่ใช่ Standalone Compile-tested Fixture
6. Execution Trace — Expected: Auto Locomotion Selects Walk → Upper-body Clip Overlays Base Pose → BoneLookAt Aims Head → Procedural Override Updates Torso → Renderer Displays Final Pose
7. Limits & Failure Modes: Crowd Instances ไม่รองรับ Bone/Pose Simcalls บางชนิด; Imported Rig อาจใช้ Local Bone Axes ต่างจาก World Axes และ Animation Layer ที่ไม่ได้ Key ครบทุก Upper-body Bone อาจทำให้บางกระดูกกลับไปอยู่ Rest Pose
8. Verification: Expected: NPC เดินไปพร้อมกับหันศีรษะมองผู้เล่นได้; Actual: Not Run สำหรับ Layering Test ใหม่
9. Disclosure Status: Animation Blending/Bone Look-at Documented; Full-body IK / Built-in State Machine Graph Undisclosed
10. Research Gaps: IK Chains, Foot Placement, Animation Graph Representation, Crossfade Internals, Root Motion Handling และ Network Animation State Replay

147 — รองรับ Behavior Trees หรือ Utility AI หรือไม่?

149 — Animation และ NPC Behavior Deterministic ใน Multiplayer อย่างไร?

แต่ไม่ควรสรุปว่า GPU Skinning หรือ Visual Animation Output ให้ภาพเหมือนกันทุก Pixel บนอุปกรณ์ต่างกัน เพราะ Render Determinism เป็นคนละประเด็นกับ Gameplay Determinism
2. Architecture: AI Decisions และ NPC World State อยู่ใน Shared Simulation ส่วน Visual Animation มีบางส่วนที่เป็น Display-only เช่น Bone Overrides/Retargeting
3. Source Evidence: multiplayer_guidance, animations, frame_and_scheduling_model, object_types
4. API Contract:
SetAIMoveVector เป็น Held Input ที่มีผลใน Frame ถัดไป ส่วน PressAIAction ทำให้เกิด Action Down ใน Frame ถัดไป และ Release โดยอัตโนมัติใน Frame ต่อมา
5. Working Example:
ตัวอย่างนี้มาจาก API Pattern ในคู่มือ และต้องอยู่ใน Event/Function ที่เหมาะสม ยังไม่ได้ทดสอบ Bot Input ในรอบนี้
6. Execution Trace — Expected: Spawn Bot → Attach #class player → Set AI Input → Next Frame Action/Move Event → Gameplay State Update → Render Animation
