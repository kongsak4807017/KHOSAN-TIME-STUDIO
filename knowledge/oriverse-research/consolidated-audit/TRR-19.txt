181 — Oriverse Asset Library จัดเก็บ Mesh, Material และ Clips อย่างไร?
1. Direct Answer: Oriverse มี Shared Asset Library สำหรับเก็บ Procedural Mesh Source พร้อม Dependencies, Material Source และ Animation Clip Source พร้อมข้อมูล Rig/Target Compatibility การ Save เป็นการเก็บ Candidate ไม่ใช่การอนุมัติว่า Asset นั้นผ่าน Quality Review แล้ว
2. Architecture: Author Asset → Save Source + Dependencies → Generate Asset Identity/Digest → Queue/Store in Library → Search/Inspect → Import into Pending World
3. Source Evidence: Tool Contracts ของ save_mesh_asset, save_material_asset, save_clip_asset, import_material_asset, import_clip_asset และผลจริงจาก library_capture_status
4. API Contract:
เครื่องมือรายงาน Storage State เช่น shared, queued for retry หรือ session-only

182 — Asset Identifiers, Revisions และ Provenance มีโครงสร้างอย่างไร?
1. Direct Answer: ผลตรวจจริงแสดง Asset IDs ที่ขึ้นต้นด้วยชนิดของ Asset และตามด้วย Hex Digest เช่น mesh_... และ material_... อีกทั้งมี digest, job_id, batch_id, parent_asset_id และ Review Receipt แต่ยังไม่พบ Contract ที่รับรองว่าโครงสร้าง ID เป็น Immutable Content-addressed Identifier ทุกกรณี
2. Architecture: Source Artifact → Asset ID/Digest → Storage Receipt → Optional Parent/Review Relationship → Import/Use in World
3. Source Evidence: library_capture_status; Tool Contracts ของ save_mesh_asset, save_clip_asset, rate_asset

183 — รองรับ Import GLB, glTF, FBX หรือ Formats ใดบ้าง?
1. Direct Answer: คู่มือยืนยันว่า Oriverse รองรับการใช้งาน Marketplace Models ที่มี Geometry และ PBR Materials และกล่าวถึง Imported GLB โดยตรง รวมถึงสามารถ Import Images และ Editable Library Assets ได้ แต่ยังไม่พบ Public Generic File Import API ที่รับ GLB, glTF หรือ FBX จากไฟล์ใดก็ได้ผ่าน MCP
2. Architecture: Marketplace Model References แตกต่างจาก Editable Procedural Library Source ส่วน Images ที่ Import เข้า Project จะถูกแปลงเป็น PNG และอ้างด้วย projimg Handle
3. Source Evidence: inspect_model, inspect_rig, import_image, use_mesh_asset; mesh_dsl_usage
4. API Contract:
inspect_model รับ Marketplace Model URLs สูงสุด 8 รายการ และคืน Geometry/LOD/Submesh/Animation Metadata; import_image รับภาพจาก HTTPS/Attachment แล้ว Normalize เป็น PNG
5. Working Example — Marketplace Model Reference:
model.Creator.AssetName เป็น Placeholder เท่านั้น ไม่ใช่ชื่อ Asset ที่ตรวจพบจริง จึงไม่ถือว่า Compile-tested
6. Execution Trace — Expected: Resolve Marketplace Asset URL → Load Model/Materials/Clips → Bind Scene Object → Render
7. Limits & Failure Modes: FBX Import, Generic .gltf Upload, Arbitrary .glb File Upload และ Direct Blender File Import ยังไม่มี Public Tool Contract ที่ยืนยันได้
8. Verification: Expected: Marketplace Models ที่ถูกต้องโหลด Geometry ได้; Actual: ตรวจสัญญาเครื่องมือแล้ว แต่ไม่ได้ Import GLB/FBX ใหม่
9. Disclosure Status: Marketplace Model/GLB Usage Documented; Generic GLB/glTF/FBX Import Not Verified
10. Research Gaps: Supported Extensions, Importer Version, glTF Extensions, Skinning/Animation Compatibility, Coordinate Conversion และ Material Fidelity
184 — Export Geometry และ Materials เป็นไฟล์มาตรฐานใด?
1. Direct Answer: จากเครื่องมือ 53 รายการที่เปิดให้ใช้ ไม่พบ Export Tool ที่ระบุว่าจะเขียน Procedural Mesh/Material เป็น .glb, .gltf, .fbx, .obj, .usd หรือ .usdz โดยตรง
สิ่งที่ยืนยันได้คือการ Save Editable Source ลง Shared Library และการสร้าง World Source เป็นข้อความ Weave
2. Architecture: Procedural Mesh/Texture Source ถูกประมวลผลเพื่อใช้ใน Oriverse Renderer แต่ยังไม่มี Published File Export Boundary ที่ตรวจได้จาก Public Tools
3. Source Evidence: Tool Inventory, save_mesh_asset, save_material_asset, preview_mesh, inspect_mesh
4. API Contract: ไม่มี Verified ExportMesh, ExportMaterial, ExportGLB หรือ ExportFBX Tool Signature ในเซสชันนี้
5. Working Example: ไม่มีตัวอย่าง Export เป็นไฟล์มาตรฐานที่ผ่านการทดสอบ จึงไม่สร้างชื่อ API สมมติขึ้นมา
6. Execution Trace: Weave Source → Procedural Bake เป็นพฤติกรรมที่มีเอกสาร ส่วน Bake → Standard 3D File Export เป็น Undisclosed
7. Limits & Failure Modes: Mesh Preview หรือ Inspect Metadata ไม่เท่ากับ Downloadable Mesh File และ Asset ID ไม่ใช่ Binary Export Artifact
8. Verification: Expected: Export Tool ควรคืน File/URL พร้อม Geometry/Material Data; Actual: No Export Tool Identified ในเซสชันนี้
9. Disclosure Status: Standard-format Geometry/Material Export Undisclosed / Not Verified
10. Research Gaps: GLB Export, Mesh Topology Preservation, UV/Normal/Tangent Export, PBR Packing, Animation Export และ Blender/Unity/Godot Compatibility
185 — สามารถ Export Weave Source และ Dependencies ทั้งหมดได้หรือไม่?
1. Direct Answer: ยืนยันได้ว่า Oriverse สามารถส่ง World Source เป็นข้อความ Weave และมีเครื่องมืออ่าน Source ปัจจุบันแบบ Read-only อีกทั้งการเผยแพร่ผ่าน publish_game ใช้ไฟล์ world_description.weave แต่ยังไม่พบเครื่องมือที่รับประกันการ Export Complete Dependency Bundle พร้อม Assets ทุกประเภทเป็นไฟล์ดาวน์โหลดชุดเดียว
2. Architecture: World ประกอบด้วย Weave Source, Local Definitions, Asset Aliases, Marketplace References, Project Images และ Dependencies ของ Mesh/Material/Animation บางประเภท
3. Source Evidence: multi_stage_projects, asset_aliases, sync_pending_world_from_current, publish_game, save_mesh_asset
4. API Contract: sync_pending_world_from_current({source:"live", preview:true}) คืน World Source แบบ Read-only โดยจำกัด 400 บรรทัดหรือ 32 KB; pending_world_read_sections อ่าน Source เป็นช่วง และ publish_game รับ Full Weave Source เป็น world_text
5. Working Example — Source ที่ตรวจสอบจริง:
ตัวอย่างนี้ดึงจาก Live World Source จริง ไม่ใช่ Source ที่สร้างขึ้นใหม่
6. Execution Trace — Observed: เรียก Live Source Preview → ได้ Weave Source 181 บรรทัด ขนาด 9,654 Bytes → Pending Draft ไม่ถูกแก้ไข → ตรวจพบ Local Mesh, Texture และ Gameplay/Scene Declarations
7. Limits & Failure Modes: Source Export ไม่ได้ครอบคลุม Marketplace Binary Assets, Image Attachments หรือ Build Artifacts โดยอัตโนมัติ และการย้าย Source โดยไม่มี Dependencies อาจทำให้ Missing Asset References
8. Verification: Expected: อ่าน Source ปัจจุบันโดยไม่แก้ Draft ได้; Actual: PASS สำหรับ Read-only Source Retrieval; Full Dependency Bundle Not Verified
9. Disclosure Status: Weave Source Retrieval Experimentally Verified; Full Portable Source+Asset Export Undisclosed
10. Research Gaps: Dependency Manifest, Asset Lockfile, Portable Bundle Format, Project Image Export, Offline Dependency Resolution และ Rebuild Reproducibility
186 — ย้ายเกมไป Unity, Godot หรือ Custom WebGPU Engine ได้เพียงใด?
1. Direct Answer: สามารถนำ แนวคิด Gameplay, World Specification และ Weave Source ไปใช้เป็นข้อมูลอ้างอิงในการ Port ได้ แต่ไม่สามารถรับรองว่า Unity, Godot หรือ Custom WebGPU Engine จะ Compile หรือ Execute Weave ได้โดยตรง
เนื่องจากยังไม่มี Verified Weave Runtime Port, Official Converter หรือ Binary Asset Export Pipeline ที่ครอบคลุม
2. Architecture: การ Port ต้องแยก Source Translation, Scene Graph Conversion, Asset Geometry/Materials, Animation, Physics, UI, Persistence และ Multiplayer Semantics เพราะ Engine แต่ละตัวมี Runtime Contracts ต่างกัน
3. Source Evidence: weave_coding → weave_language, mesh_dsl_usage, multi_stage_projects, asset_aliases และ Tool Inventory ที่ตรวจพบ
4. API Contract: ไม่มี Verified ExportUnityProject, ExportGodotProject, ExportWebGPUScene หรือ Cross-engine Runtime API

187 — Asset Conversion และ Interoperability APIs
1. Direct Answer: Oriverse มี API สำหรับนำ Editable Library Assets เข้าสู่ Pending World พร้อม Dependencies และตรวจ Rig Compatibility แต่ยังไม่มี Public Contract ที่ระบุการแปลง Arbitrary 3D Files จาก/ไปมาตรฐานภายนอกอย่างครบถ้วน
2. Architecture: Asset Library → Read Exact Asset ID → Validate Target/Snapshot → Import Source and Dependencies → Resolve Naming Collisions → Revalidate Pending World
3. Source Evidence: use_mesh_asset, import_material_asset, import_clip_asset, inspect_model, inspect_rig, import_image
4. API Contract:
import_clip_asset มี dry_run สำหรับตรวจ Rig Compatibility โดยไม่แก้ Draft และอาจคืน adaptation_required เมื่อ Bind Rig ไม่ตรงกัน
5. Working Example — Read-only Compatibility Check:
เป็นตัวอย่าง Call Pattern ตาม Schema ยังไม่ได้รันกับ Asset ID จริง
6. Execution Trace — Expected: Resolve Asset → Check Dependencies → Verify Rig/Target → Check Snapshot → Import Editable Source หรือ Reject with Compatibility Error
7. Limits & Failure Modes: Stale expected_snapshot ทำให้ Import ถูกปฏิเสธ และ Name Collision อาจทำให้ Asset ถูกตั้งชื่อใหม่ จึงต้องใช้ชื่อจริงจาก Tool Response
นอกจากนี้เครื่องมือค้นหา Library รุ่นเดิมที่ทดสอบในรอบนี้คืน INVALID_ARGUMENT พร้อมข้อความให้เปลี่ยนไปใช้ find_library_assets และ read_library_asset จึงยังไม่สามารถรับรอง Workflow การค้นหาแบบเดิมได้
8. Verification: Expected: Imported Asset พร้อม Dependencies และ Rig Compatibility ถูกต้อง; Actual: Tool Contracts ได้รับการตรวจ แต่ Import Round-trip Not Run; Legacy Library Search FAILED/REPLACED
9. Disclosure Status: Source-level Library Import Documented; Current Search Migration Observed; Generic File Conversion Undisclosed
10. Research Gaps: New Library Tool Schemas, Importer Versioning, External File Conversion, Material Fidelity, Animation Retargeting และ Dependency Conflict Resolution
188 — License ของ Generated Assets และ Library Assets เป็นอย่างไร?
1. Direct Answer: จากคู่มือและ Tool Contracts ที่ตรวจในรอบนี้ ยังไม่พบข้อกำหนดสิทธิ์ใช้งานที่เพียงพอ สำหรับสรุปว่า Generated Assets, Shared Library Assets หรือ Marketplace Assets สามารถนำไปใช้เชิงพาณิชย์ แจกจ่ายต่อ ดัดแปลง หรือ Export ไปใช้ใน Engine อื่นได้โดยไม่มีข้อจำกัด
ต้องแยก ความสามารถทางเทคนิคในการเข้าถึง Asset ออกจาก สิทธิ์ตามสัญญาอนุญาต อย่างชัดเจน
2. Architecture: ระบบมี Asset Library, Asset Identity, Storage Receipts และ Review Evidence แต่ยังไม่พบ License Metadata Schema หรือ License Enforcement Contract ที่ครบถ้วนในผลตรวจครั้งนี้
3. Source Evidence: asset_vocabulary, asset_aliases; Tool Contracts ของ save_mesh_asset, save_material_asset, save_clip_asset, rate_asset, share_game และ publish_game
4. API Contract: Tool Responses ที่ตรวจพบมี asset_id, digest, storage_state, parent_asset_id และ Review Metadata แต่ไม่พบ Field ที่รับรอง License เช่น license_id, commercial_use_allowed, redistribution_allowed หรือ attribution_required
5. Working Example — Proposed License Manifest สำหรับ KHOSAN:
นี่เป็น Schema ที่เสนอให้ KHOSAN ออกแบบเอง ไม่ใช่ Oriverse License API
6. Execution Trace — Proposed: Select Asset → Retrieve Terms/Provenance → Check License → Record Usage Scope → Approve or Block Export
7. Limits & Failure Modes: Asset ที่อยู่ในสถานะ shared ไม่ได้หมายความว่าเป็น Public Domain และการอนุญาตให้เล่นเกมผ่าน share_game ไม่ได้พิสูจน์สิทธิ์ในการแจกจ่าย Asset Binary แยกต่างหาก
8. Verification: Expected: ได้ License Terms จากเจ้าของสิทธิ์หรือเอกสารทางการและบันทึก Usage Rights; Actual: Not Verified สำหรับเงื่อนไขสิทธิ์รายประเภท
9. Disclosure Status: Asset Storage/Sharing Capabilities Documented; License Grants/Restrictions Undisclosed / Not Verified
10. Research Gaps: Oriverse Terms of Service, Generated Content Ownership, Marketplace Creator Licenses, Attribution, Redistribution, Commercial Use และ External-engine Rights
189 — รองรับ Offline Builds และ Self-hosted Runtime หรือไม่?
1. Direct Answer: Oriverse รองรับการทำงานผ่าน Editor, การ Share เกม และการ Publish Public Playable Project แต่ยังไม่พบเครื่องมือหรือคู่มือที่ยืนยันว่า สามารถ Build Runtime แบบ Standalone สำหรับนำไปติดตั้งบน Server ของตนเอง หรือใช้งานแบบ Offline โดยไม่พึ่งพาบริการ Oriverse ได้อย่างครบถ้วน
2. Architecture: Public Delivery Paths ที่ยืนยันได้คือการเสนอ World ให้ Editor โหลด การแชร์เกมผ่าน Oriverse และการเผยแพร่เป็น Oriverse Project ส่วน Offline Packaging และ Dedicated Server Deployment ไม่ได้มี Tool Contract ที่ตรวจพบ
3. Source Evidence: submit_pending_world, share_game, show_game, publish_game, request_project_save
4. API Contract:
share_game คืน Public Play Link ที่มีอายุประมาณ 30 วัน ส่วน publish_game สร้างหรืออัปเดต Public Playable Project และคืน Permanent Project Page URL
5. Working Example — ตัวอย่าง Delivery Contract:
