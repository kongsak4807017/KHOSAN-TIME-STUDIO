151 — #sound DSL สร้างเสียงและจัดการ Asset อย่างไร?
1. Direct Answer: #sound Name ... #end เป็น DSL สำหรับสังเคราะห์เสียง Procedural แบบ SFX โดยนำ Oscillators, Noise, Envelopes และ Filters มาประกอบเป็น Signal และ Bake เป็น Local Sound Asset เมื่อโหลด World
ข้อจำกัดสำคัญคือ ความยาวเสียงสูงสุด 8 วินาที จึงไม่ใช่เครื่องมือแต่งเพลงหรือสร้าง BGM ยาวโดยตรง
2. Architecture: Sound Definition → Evaluate Signal Expressions → Bake Sound Asset → Reference Ori.sound.name → Trigger Playback
3. Source Evidence: weave_coding → sound_dsl_usage
4. API Contract:

5. Working Example — ตัวอย่างจากคู่มือ Oriverse:
เรียกใช้งานด้วย PlaySound(Ori.sound.laser, 1.0) ใน Event หรือ Function ที่เหมาะสม
6. Execution Trace — Expected: Read #sound → Evaluate Sweep/Filter/Envelope → Bake Asset → Gameplay Triggers PlaySound → Playback
7. Limits & Failure Modes: ไม่มี Instrument Sequencer สำหรับ Music Composition การแก้ Sound Definition ต้อง Reload เพื่อ Bake ใหม่ และการใช้เสียงยาวเกิน 8 วินาทีไม่อยู่ใน Contract
8. Verification: Expected: เสียง Laser ถูก Bake และเล่นหนึ่งครั้งเมื่อเรียก API; Actual: ตัวอย่างมาจากคู่มือโดยตรง แต่ ยังไม่ได้ Compile หรือฟังเสียงจริงในรอบนี้
9. Disclosure Status: Sound DSL Documented; Runtime Playback Test Not Verified
10. Research Gaps: Sample Rate, PCM Encoding, Compression, Asset Cache, Bake Cost และ Audio Thread Implementation
152 — Spatial Audio และ Attenuation ทำงานอย่างไร?
1. Direct Answer: Oriverse แยก Global Audio Playback จาก Positional Playback โดยคู่มืออธิบายว่า PlaySound เป็นเสียงที่เล่นทั่วทุก Client ด้วยระดับเสียงตามที่กำหนด ส่วน PlaySoundAtPosition รองรับ Positional Attenuation ตามผู้ฟัง
อย่างไรก็ตาม ยังไม่มีหลักฐานเพียงพอที่จะระบุสูตร Distance Attenuation, Spatialization Algorithm, HRTF หรือ Occlusion Model
2. Architecture: Gameplay เรียก Sound Asset ที่ World Position → Audio System ประเมินตำแหน่งผู้ฟังแต่ละ Client → Playback Output
3. Source Evidence: weave_coding → built_in_function_list → PlaySound ซึ่งระบุ Positional Playback ด้วย PlaySoundAtPosition
4. API Contract:
สำหรับ PlaySoundAtPosition ยืนยันได้ว่ามี API ตามคำอธิบายของ PlaySound แต่ยังไม่ได้รับ Exact Declaration ในผลตรวจรอบนี้ จึงไม่ระบุ Signature โดยคาดเดา
5. Working Example:
เป็นตัวอย่าง Global Sound ที่ใช้ API Signature จริง ไม่ใช่การทดสอบ Spatial Attenuation
6. Execution Trace — Expected: Trigger Event → Resolve Sound Asset → Resolve Listener Position สำหรับ Positional Call → Apply Attenuation → Output Audio
7. Limits & Failure Modes: การใช้ PlaySound สำหรับเสียงฝีเท้าหรือเสียงจาก NPC อาจทำให้ผู้เล่นทุกคนได้ยินโดยไม่ขึ้นกับระยะ หากต้องการเสียงเฉพาะตำแหน่งควรใช้ Positional API
8. Verification: Expected: Global Sound ได้ยินทุก Client; Positional Sound ลดระดับตามระยะ; Actual: Not Run สำหรับ Distance/Attenuation Matrix
9. Disclosure Status: Global/Positional Playback Documented; Exact Attenuation Curve Undisclosed
10. Research Gaps: Distance Model, HRTF, Stereo Panning, Doppler, Occlusion, Reverb และ Listener Mixing Rules
153 — Audio Mixing, Buses และ Priorities ทำงานอย่างไร?
1. Direct Answer: Oriverse เปิดเผยการควบคุมระดับเสียงและการหยุดเสียงในระดับ Asset รวมถึง Looped Playback แต่ยังไม่พบ Audio Bus Graph, Priority-based Voice Stealing หรือ Audio Ducking Contract ที่ยืนยันได้
2. Architecture: Sound Playback สามารถเปิดหลาย Instances ของ Asset และควบคุม Volume ของ Asset ทั้งหมดได้ด้วย SetSoundVolume
3. Source Evidence: Built-in API Lookup ของ PlaySoundLooped, StopSound, SetSoundVolume
4. API Contract:
SetSoundVolume มีผลกับ Instances ที่กำลังเล่น รวมถึง Loops และการ Play ครั้งต่อไป ค่า 0 ทำให้เงียบแต่ไม่ได้หยุด Loop
5. Working Example:
เป็นตัวอย่าง API Composition ไม่ใช่แนวทางที่แนะนำให้ Loop เสียง Laser จริง และยังไม่ได้รัน
6. Execution Trace — Expected: Start Loop → Change Asset Gain → All Instances Reflect Gain → Stop All Instances of Asset
7. Limits & Failure Modes: StopSound หยุดทุก Instances ของ Asset เดียวกัน ไม่ใช่หยุด Instance ID เฉพาะราย และไม่ได้รับรองว่า Engine รองรับ Named Buses เช่น Music/SFX/Voice แบบที่ผู้พัฒนากำหนดเอง
8. Verification: Expected: เปลี่ยน Volume แล้ว Loop มีความดังเปลี่ยน; Actual: Not Run
9. Disclosure Status: Asset-level Mixing Documented; Bus/Priority System Undisclosed
10. Research Gaps: Mixer Topology, Max Concurrent Voices, Priority Policy, Voice Virtualization, Ducking, Loudness Normalization และ Output Device Handling
154 — #particles สร้างและอัปเดต Particle Systems อย่างไร?
1. Direct Answer: #particles ใช้ JSON Array ของ Emitter Components และรองรับ Billboard, Mesh และ Ribbon Particles พร้อม Emission, Lifetime, Velocity, Acceleration, Color/Opacity Curves, Flipbooks และ Procedural Shader Materials
2. Architecture: Emitter Configuration → Effect Asset → Spawn Effect Object → Emit/Update Particles → Render/Destroy ตาม Lifecycle
3. Source Evidence: particle_vfx, weave_coding → particles_json_usage

6. Execution Trace — Expected: Load Effect → Spawn Emitter → Emit Particles at Rate → Integrate Motion/Lifetime → Fade → Remove Dead Particles
7. Limits & Failure Modes: Particle Components แบบ Mesh มีต้นทุนสูงเพราะแต่ละตัวเป็น Lit Draw; คู่มือแนะนำให้ spawnRate × lifeTime ต่ำกว่าประมาณ 100 ต่อ Mesh Component และ boundingBoxSize ต้องกำหนดเพื่อป้องกัน Scale ผิด
8. Verification: Expected: Sparks ปรากฏและหายไปตาม Lifetime; Actual: Not Run
9. Disclosure Status: Particle DSL Documented; Internal CPU/GPU Simulation Undisclosed
10. Research Gaps: Particle Buffer Layout, Update Backend, Sorting, GPU Culling, Max Particle Counts และ Cross-device Performance
155 — VFX ผูกกับ Event และ Object Lifecycle อย่างไร?
1. Direct Answer: Weave สามารถ Spawn VFX เมื่อเกิด Gameplay Event และผูก Effect กับ Object/Anchor เพื่อให้เคลื่อนที่ตาม Parent ได้ รองรับการปิด Emission โดยปล่อยให้ Particles ที่มีอยู่เล่นจนจบ
2. Architecture: Gameplay Event → SpawnEffect → Attach/Follow Parent → Emit → Stop Emitting → Destroy After Remaining Particles
3. Source Evidence: particles_json_usage, particle_vfx; Built-in Functions SpawnEffectWithAutoDestroy, SpawnEffectAttached, SetEmitting, DestroyAfterParticles
4. API Contract:
SpawnEffectAttached ติดตาม Anchor ของ Parent โดย Duration <= 0 ให้ใช้ Lifetime ตาม Effect Definition
5. Working Example:
ต้องมี #particles SmallSparks อยู่ใน World เดียวกัน และยังไม่ได้ทดสอบ Runtime
6. Execution Trace — Expected: Click Object → Spawn Effect → Emit Burst → Lifetime Ends → Effect Auto-destroyed
7. Limits & Failure Modes: การ Destroy Emitter ทันทีอาจตัด Particles ที่ยังไม่จบ คู่มือจึงแนะนำ DestroyAfterParticles() สำหรับ Continuous/Attached Effects และหลีกเลี่ยงการ Destroy/Respawn ทุกครั้งที่เปลี่ยนทิศทาง
8. Verification: Expected: Effect แสดงเต็ม Lifetime และถูกลบหลังจบ; Actual: Not Run
9. Disclosure Status: Effect Lifecycle Documented; Particle Scheduling Internals Undisclosed
10. Research Gaps: Parent Destruction Semantics, Effect Completion Events, Lifetime Precision, Rollback Behavior และ Visual Synchronization
156 — Shader Effects เช่น Wind, Dissolve และ Flow ทำงานอย่างไร?
1. Direct Answer: #shader ของ Oriverse รองรับ Raw WGSL Hooks สำหรับแก้ Vertex Positions และ Surface Parameters จึงสามารถสร้าง Wind, Dissolve, Flow, Emission Pulses และ Fullscreen Distortion ได้
2. Architecture: Shader ถูกผูกกับ Material แล้ว Engine Inject Code เข้า Standard Lit Pipeline โดย @vertex ปรับ Geometry และ Fragment Body เขียน Surface Outputs
3. Source Evidence: shader_dsl → Structure, Runtime control, Particle shaders, Screen shaders
4. API Contract:
Runtime Scalar Parameters สูงสุด 32 Slots ต่อ Material ผ่าน SetMaterialParameterNumber และ WGSL อ่านผ่าน mat.params4
5. Working Example — จากคู่มือ Shader:
6. Execution Trace — Expected: Material Bind → WGSL Compile → Vertex Offset by Time/Noise → Fragment Surface Evaluation → Engine Lighting → Final Image
7. Limits & Failure Modes: Shader Space เป็น Y-up หน่วยเมตร ต่างจาก Weave Simulation ที่เป็น Z-up หน่วยเซนติเมตร และ WGSL Compile Failure อาจทำให้ Material ใช้ Default Rendering
8. Verification: Expected: ใบไม้ไหวตามเวลา; Actual: ตัวอย่างจากคู่มือ แต่ไม่ได้ Render/Compile ในรอบนี้
9. Disclosure Status: WGSL Hooks Documented; Shader Compiler/Pipeline Internals Undisclosed
10. Research Gaps: Shader Variant Caching, GPU Cost, Vertex Deformation Motion Vectors, Material Instance Isolation และ Device Compatibility

158 — Animation/VFX Synchronization กับ Audio มีอย่างไร?
1. Direct Answer: Oriverse รองรับการจัดจังหวะ Animation Contact ผ่าน PlayAnimationHittingContactIn และ GetAnimationLeadSeconds ซึ่งช่วยให้ Gameplay Event, Hit Contact, Audio และ VFX ถูกเรียกให้สัมพันธ์กับจังหวะเดียวกันได้
แต่ยังไม่พบ Public Event Marker Track สำหรับ Animation/Audio/VFX Synchronization โดยตรงในรูปแบบที่เปิดเผยครบถ้วน
2. Architecture: Gameplay กำหนดเวลาที่ต้องการให้เกิด Contact แล้ว Animation System ปรับ Playback Rate เพื่อให้ Contact Percent ตรงกับเวลานั้น จากนั้นสามารถเรียกเสียงและ VFX ณ Gameplay Event ที่ต้องการได้
3. Source Evidence: weave_coding → animations; Built-in API Lookup ของ PlayAnimationHittingContactIn
4. API Contract:
PlayAnimationHittingContactIn คืน false เมื่อยังเร็วเกินไป และปรับอัตราการเล่นในช่วงประมาณ 0.5×–2× เพื่อให้ Contact Percent ตรงเวลา
5. Working Example:
6. Execution Trace — Expected: Attack Scheduled → Animation Waits for Valid Start Window → Clip Plays Rate-adjusted → Contact Percent Reaches Target Time → Gameplay May Trigger Sound/VFX
7. Limits & Failure Modes: การเรียก Sound ทันทีเมื่อฟังก์ชันคืน true อาจไม่ตรง Contact Frame เพราะ true หมายถึง Animation เริ่มแล้ว ไม่ใช่ Contact เกิดขึ้นแล้ว ต้องใช้ Timing Contract หรือ State/Timer ที่สอดคล้องกัน
8. Verification: Expected: Animation Contact ตรงกับ Target Time; Actual: Not Run สำหรับ Audio/VFX Sync Matrix
9. Disclosure Status: Animation Contact Timing Documented; Audio/Particle Sync Precision Not Verified
10. Research Gaps: Sample-accurate Audio Scheduling, Animation Notifies, VFX Event Markers, Latency Compensation และ Cutscene Track Synchronization
159 — Multiplayer Synchronization ของ Effects
1. Direct Answer: Oriverse ใช้ Deterministic Lockstep สำหรับ Shared Gameplay State โดยสามารถเรียก VFX/Audio จาก Gameplay Events ที่ทุกฝ่ายจำลองร่วมกันได้ แต่ยังไม่มีหลักฐานเพียงพอให้รับรองว่าเสียงและภาพจาก Particle/Shader จะเหมือนกันแบบ Sample-accurate หรือ Pixel-identical บนอุปกรณ์ต่างกัน
2. Architecture: Gameplay Event ถูกประมวลผลผ่าน Shared Simulation ส่วนการแสดงผล Audio/Visual ถูกสร้างบน Client ตาม State และ Runtime/Rendering Context ของแต่ละ Viewer
3. Source Evidence: multiplayer_guidance, frame_and_scheduling_model, particles_json_usage, shader_dsl
4. API Contract: ใช้ SpawnEffectWithAutoDestroy, SpawnEffectAttached, PlaySound, PlaySoundAtPosition และ Shader/Material Parameters ตาม Public APIs
5. Working Example:
ต้องมี Effect/Sound Definitions ที่ถูกต้อง และไม่ได้ทดสอบ Multi-client Execution
6. Execution Trace — Expected: Shared Input → Gameplay Event → Shared Simulation State Updates → Each Client Renders Effect/Plays Sound
7. Limits & Failure Modes: Audio Playback Latency, Particle Timing และ Shader Time-dependent Effects อาจแตกต่างระหว่างอุปกรณ์ และคู่มือยังไม่เผยว่า Rollback จัดการ One-shot Audio/VFX Duplicates อย่างไร
8. Verification: Expected: ผู้เล่นทั้งสองฝ่ายเห็น/ได้ยินผลตาม Gameplay Event เดียวกัน; Actual: Not Run สำหรับ Cross-client A/V Sync Test
9. Disclosure Status: Shared Simulation Documented; Exact A/V Synchronization Guarantees Undisclosed
10. Research Gaps: Rollback-safe Effect IDs, Audio Deduplication, Prediction Effects, Visual Event Replay, Network Clock Alignment และ Latency Compensation
