191 — Weave Sandbox จำกัดสิทธิ์ของเกมและสคริปต์อย่างไร?
1. Direct Answer: Weave เป็นภาษาเฉพาะสำหรับสร้าง Gameplay และ Scene โดย Compiler อนุญาตให้เรียก Built-in APIs ตามชนิดและบริบทที่กำหนด ไม่ได้ให้ความสามารถแบบ JavaScript, Python หรือ Native Code ทั่วไปผ่าน #class
ส่วน #html เป็น HTML/CSS Subset ที่ไม่รองรับ JavaScript, Browser Navigation และ General-purpose Forms
อย่างไรก็ตาม ยังไม่สามารถยืนยันว่า Runtime ใช้ OS Process Sandbox, WASM Isolation หรือ Memory-safe VM Architecture แบบใดภายใน
2. Architecture: ขอบเขตที่มีหลักฐานคือ Weave Source → Compiler/Type Validation → Bytecode → Engine-defined Simulation APIs ส่วน UI อยู่ภายใต้ Parser และ Binding Contracts ของ Oriverse

192 — ป้องกัน Malicious Code และ Resource Exhaustion อย่างไร?
1. Direct Answer: Oriverse มี Compiler Restrictions และ Resource Limits เพื่อควบคุมการใช้ทรัพยากรบางประเภท เช่น Continuations, Lists, Objects และ Runtime Operations
โดยเฉพาะ Global Continuation Budget 262,144 Slots และข้อห้าม Recursion ใน Weave2
แต่ยังไม่พบข้อมูลยืนยัน Instruction Fuel, Memory Quota ต่อ Game, GPU Timeout Policy หรือ Rate Limiting ทุก API
2. Architecture: การป้องกันระดับที่เปิดเผยประกอบด้วย Compile-time Validation, Runtime Resource Caps และข้อจำกัดของ Built-in Operations

10. Research Gaps: CPU Fuel Limits, GPU Shader Watchdog, Memory Quotas, Per-user Rate Limits, Fuzz Testing และ Resource Isolation Between Games
193 — ตรวจและอนุญาต User-generated Content อย่างไร?
1. Direct Answer: Oriverse มีเครื่องมือสร้าง/Import Images, Assets, Weave Source และ Public Game Projects พร้อม Validation, Library Review และบางกรณีใช้ User Approval ผ่าน Editor แต่ยังไม่พบ Public UGC Moderation Policy/API ที่เปิดเผยครบสำหรับการตรวจเนื้อหา รูปภาพ ข้อความ และเกมก่อนเผยแพร่
2. Architecture: เครื่องมือที่สังเกตได้รองรับ Source Validation → Asset Inspection → Storage/Review → Publish อย่างไรก็ตาม Content Safety Moderation และ Rights Review ไม่ควรถูกอนุมานว่ารวมอยู่ใน Pipeline ดังกล่าวโดยอัตโนมัติ
3. Source Evidence: save_mesh_asset, save_material_asset, rate_asset, import_image, generate_image, publish_game
4. API Contract: rate_asset รองรับ Verdict good, bad, wrong_style พร้อม evidence_id จาก Preview แต่เป็นการตรวจความเหมาะสมของ Asset สำหรับ Use Case ไม่ใช่ Content Moderation Approval
5. Working Example — Proposed UGC Review Record:
นี่เป็น Schema สำหรับ KHOSAN ไม่ใช่ Oriverse API
6. Execution Trace — Proposed: Submit UGC → Validate Source/Format → Scan Content/Rights → Human Review When Required → Approve/Reject → Publish With Audit Record
7. Limits & Failure Modes: Asset Storage State shared ไม่ได้ยืนยันว่าเนื้อหาปลอดภัย ถูกลิขสิทธิ์ หรือได้รับอนุญาตสำหรับทุกกลุ่มอายุ
8. Verification: Expected: UGC ที่ไม่ผ่าน Policy ถูก Block ก่อน Publish; Actual: Not Verified ว่า Oriverse ใช้ Policy/Workflow ดังกล่าวอย่างไร
9. Disclosure Status: Asset Validation/Review Tooling Documented; Content Moderation System Undisclosed
10. Research Gaps: Moderation Categories, Appeal Process, Abuse Reporting, Age Ratings, Copyright Claims, Automated Scanning และ Enforcement Transparency
194 — Account Authentication และ Project Permissions
1. Direct Answer: Oriverse มี Authenticated Account/Project Ownership Boundaries ตามสัญญาเครื่องมือ เช่น การสร้างภาพและ Import ภาพต้องมี Editor ที่ Signed-in และมีสิทธิ์เขียน Project ส่วน publish_game ทำงานกับ Public Project ของบัญชีผู้เรียก
แต่ไม่พบเอกสารระบุ Authentication Protocol เช่น OAuth/OIDC Session Token Structure, RBAC Matrix หรือ Server-side Authorization Logic

196 — Version Rollback, Backup และ Recovery
1. Direct Answer: Oriverse รองรับการกู้คืน World Source หลายแหล่งผ่านเครื่องมือ Editor เช่น Live, Failed Submission, Persisted Draft และ Last Successfully Loaded World รวมถึงรองรับ Named Game Saves และ Cloud Save Conflict Resolution ในเกมที่เผยแพร่
แต่ ยังไม่พบข้อรับรองว่า Project Source มี Full Version-control History, Automatic Backups หรือ Point-in-time Recovery ตามระยะเวลาที่กำหนด
2. Architecture: ต้องแยก Recovery สองชั้น คือ Project/World Source Recovery กับ Player Gameplay Save Recovery เพราะเป็นข้อมูลคนละประเภท
3. Source Evidence: sync_pending_world_from_current, submit_pending_world, persistent_state_v1, example_html_game_saves
4. API Contract:
สำหรับ Personal Saves มี RequestCreateGameSave, RequestLoadGameSave, RequestOverwriteGameSave, RequestDeleteGameSave และ RequestResolveGameSave
5. Working Example — Read-only Recovery Inspection:
คำสั่ง preview:true ตรวจ Source โดยไม่แทนที่ Pending Draft
6. Execution Trace — Expected: World Load Failed → Inspect Failed/Lastworld Source → Compare Changes → Restore Appropriate Snapshot → Compile/Playtest → Submit Revised World
7. Limits & Failure Modes: การใช้ Recovery Source ผิดอาจทำให้การแก้ล่าสุดสูญหาย ส่วน @persist Migration มี Validation เช่นการลบหรือเปลี่ยนชนิด Fields อาจถูกปฏิเสธเพื่อป้องกัน Progress Damage
นอกจากนี้ Save Status saved_on_device ไม่ได้หมายถึงข้อมูล Sync ไป Cloud แล้ว
8. Verification: Expected: Recovery Preview ไม่แก้ Draft และสามารถระบุ Snapshot เพื่อกู้คืนได้; Actual: Tool Contract ยืนยัน แต่ยังไม่ได้ทดลองกู้คืน Failed Project หรือ Cloud Save Conflict ในรอบนี้
9. Disclosure Status: Recovery Sources / Game Saves Documented; Full Backup SLA / Project History Undisclosed
10. Research Gaps: Backup Frequency, Snapshot Retention, Disaster Recovery RPO/RTO, Cloud Sync Guarantees, Version Diff และ Production Rollback
