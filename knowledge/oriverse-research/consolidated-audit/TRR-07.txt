หมวด 07: Multiplayer, Lockstep & Rollback | คำถาม 061–070 | 8 ตุลาคม 2569
ผมเชื่อมต่อ Oriverse และตรวจคู่มือโดยตรง ได้แก่ weave_coding → multiplayer_guidance, frame_and_scheduling_model, events, event_list, persistent_state_v1 และ world_rules
ผลสำคัญคือ Oriverse ระบุชัดเจนว่า Multiplayer ใช้ Deterministic Lockstep พร้อม Client Prediction และ Rollback ไม่ใช่ระบบที่ส่ง Object State ทุกตัวเป็นหลัก (Object Replication) แต่คู่มือยังไม่เปิดเผยรายละเอียด Packet Format, Input Sequencing Protocol, Snapshot Encoding, State Hash Algorithm และ Network Security Implementation
รายงานนี้จึงแยกสามระดับหลักฐาน: สิ่งที่คู่มือระบุโดยตรง, สิ่งที่อนุมานได้เชิงสถาปัตยกรรม และสิ่งที่ยังไม่ได้รับการเปิดเผย

061 — Deterministic Lockstep ทำงานอย่างไรโดยละเอียด?
1. Direct Answer: คู่มือระบุว่าผู้เข้าร่วมใช้ World, Weave Code และ Inputs ที่สอดคล้องกันเพื่อให้ Simulation State ได้ผลตรงกัน โดย Gameplay Logic เปลี่ยน Shared Simulation State ตามปกติ ผู้พัฒนาไม่ต้องเขียน Per-object Replication เอง
2. Architecture: แต่ละ Client/Server ประมวลผล World และ Input Stream ที่สัมพันธ์กัน ส่วนความแตกต่างเฉพาะ Viewer ได้แก่ PlayerObject ที่เป็นของตนเอง Camera, Input และ UI Ownership
3. Source Evidence: multiplayer_guidance → Core model
4. API Contract: #class player ถูกผูกให้ทุก PlayerObject; GetPlayerIndex() ใช้แยกผู้เล่น; GetAllPlayers() ใช้อ่านผู้เล่นที่มีอยู่; SetPlayerOwnerIndex() ใช้กำหนดเจ้าของ UI
5. Working Example: ตัวอย่าง Player-specific State ตามคู่มือ:
6. Execution Trace — Expected: Player A Join → สร้าง PlayerObject A → Player B Join → สร้าง PlayerObject B → Inputs ถูกประมวลผลผ่าน Simulation → Shared State เปลี่ยนตาม Logic เดียวกัน
7. Limits & Failure Modes: การเก็บ Coins ของผู้เล่นทุกคนไว้ใน Manager Field เดียวจะทำให้กลายเป็น Shared Value ไม่ใช่ Per-player State และห้ามพึ่งพาลำดับ OnSpawned ข้าม Objects
8. Verification: Expected: เมื่อผู้เล่นสองคนมี State แยกกัน การแก้ Coins ของ A ไม่กระทบ Coins ของ B; Actual: คู่มือรองรับรูปแบบดังกล่าว แต่ยังไม่ได้รัน Isolated Test ในรอบนี้
9. Disclosure Status: Documented สำหรับ Core Multiplayer Model; Internal Lockstep Protocol Undisclosed
10. Research Gaps: Input Barrier Policy, Lockstep Window, Authority Election, Deterministic State Schema และ Replay Protocol
062 — Input Packets ถูกจัดลำดับและกระจายอย่างไร?
1. Direct Answer: คู่มือเปิดเผยว่า Input Events ของผู้เล่นถูกประมวลผลใน Deterministic Simulation และมี Per-player Input Variants แต่ยังไม่ระบุ Packet Header, Sequence Number, Acknowledgment, Reliable/Unreliable Channels หรือ Input Distribution Algorithm
2. Architecture: Input ของผู้เล่นเข้าสู่ Simulation ผ่าน Keyboard, Mouse และ Action Events โดยใน Weave สามารถเลือก Events ที่ผูกกับผู้เล่นเจ้าของ Object หรือ Events ที่ Broadcast ได้
3. Source Evidence: multiplayer_guidance → Per-player input; events, event_list
4. API Contract:
การใช้ Event ที่ไม่มี ByThisPlayer อาจส่งให้ Handler ของหลาย Instances ทำงานตามคู่มือ
5. Working Example:
6. Execution Trace — Expected: Local Input → Input Event → Player-specific Handler → State Mutation → Deterministic Simulation
นี่ไม่ใช่ Packet-level Trace
7. Limits & Failure Modes: หากใช้ Broadcast Input ใน #class player โดยไม่กรอง Event.Presser อาจทำให้ Action เดียวถูกประมวลผลหลายครั้งเมื่อมีผู้เล่นหลายคน
8. Verification: Expected: กด E โดย Player A แล้ว Handler ที่ผูกกับ A ตอบสนอง; Actual: Not Run
9. Disclosure Status: Input Event Semantics Documented; Packet Ordering/Distribution Undisclosed
10. Research Gaps: Wire Protocol, Input Framing, Sequence IDs, Resend Policy, Deduplication และ Tick Assignment
063 — Client Prediction คำนวณสถานะล่วงหน้าอย่างไร?
1. Direct Answer: คู่มือระบุชัดว่าใช้ Client Prediction และอธิบายบางเงื่อนไขของ Deterministic Randomness แต่ยังไม่เปิดเผย Prediction Horizon, Local Input Buffer หรือ Correction Policy
2. Architecture: ตามแนวคิด Client Prediction ผู้เล่นสามารถเห็นผลตอบสนองก่อนกระบวนการยืนยันข้อมูลครบถ้วน แต่ไม่สามารถสรุปขั้นตอนภายในของ Oriverse จากหลักการทั่วไปนี้เพียงอย่างเดียว
3. Source Evidence: multiplayer_guidance → Core model, Determinism caveats
4. API Contract: คู่มือระบุว่า RandomNumber และ RandomPosition* ใช้ Deterministic Seeding โดยสำหรับ Player Input Events จะผูก Seed กับ Input Edge เพื่อให้ Predicted Result สอดคล้องกับ Final Result
5. Working Example:
6. Execution Trace — Expected: Player Input E → Local Predicted State เพิ่ม Actions → Deterministic Simulation ประมวลผล Input → State สอดคล้องกัน
7. Limits & Failure Modes: คู่มือระบุว่า RandomChancePercent นอก Input Events ให้ผล false ระหว่าง Client Prediction จึงไม่ควรใช้กับ Combat Logic ที่ต้องตอบสนองทันที
8. Verification: Expected: Predict และ Final State ตรงกันเมื่อ Inputs เหมือนกัน; Actual: Not Run สำหรับ Prediction Test
9. Disclosure Status: Client Prediction Existence Documented; Prediction Implementation Undisclosed
10. Research Gaps: Prediction Buffer, Rollback Trigger, Client Correction, Reconciliation Rules และ Visual Smoothing
064 — Rollback เก็บ Snapshot และ Replay Simulation อย่างไร?
1. Direct Answer: คู่มือยืนยันว่ามี Rollback และระบุว่าวัตถุจำนวนมากเพิ่มต้นทุนของ Rollback State แต่ไม่เปิดเผย Snapshot Format, Snapshot Interval, Memory Compression หรือ Replay Algorithm
2. Architecture: Rollback ต้องอาศัยสถานะ Simulation ที่สามารถกลับไปยังจุดก่อนหน้าและประมวลผลต่อได้ แต่ยังไม่มีหลักฐานว่า Oriverse ใช้ Full Snapshots, Delta Snapshots หรือ State Journaling แบบใด
3. Source Evidence: multiplayer_guidance → Core model; frame_and_scheduling_model → Dense pickup/particle fields
4. API Contract: ไม่มี Public Snapshot/Restore API สำหรับ Rollback ภายในที่ยืนยันได้จากเอกสารที่ตรวจสอบ
5. Working Example: ไม่มีตัวอย่าง Raw Rollback Snapshot ที่เปิดเผย จึงไม่สร้างตัวอย่าง Binary Snapshot ขึ้นมาเอง
6. Execution Trace: เป็นไปได้ในเชิงแนวคิดว่า Late Input/Correction → Restore Prior State → Replay Inputs → Corrected Present State แต่ขั้นตอนจริงของ Oriverse ยัง Undisclosed
7. Limits & Failure Modes: การสร้างวัตถุเกมที่ต้องมี State จำนวนมาก เช่น Pickups หลายพันชิ้น อาจเพิ่ม Rollback Memory และ Simulation Cost
8. Verification: Expected: เกมรักษาความสอดคล้องหลัง Correction; Actual: Not Run และไม่มี Snapshot Trace
9. Disclosure Status: Rollback Support Documented; Snapshot/Replay Implementation Undisclosed
10. Research Gaps: Snapshot Granularity, Serialization, Rollback Window, Replay Cost และ Rollback Metrics
065 — State Hash และ Desynchronization Detection ทำงานอย่างไร?
1. Direct Answer: คู่มือ Oriverse ระบุว่า Simulation State สามารถตรวจสอบความสอดคล้องกันได้ และอธิบายระบบ Deterministic Lockstep แต่ยังไม่เปิดเผย State Hash Algorithm, Hash Coverage, Comparison Frequency หรือขั้นตอน Recovery เมื่อพบ Desynchronization
2. Architecture: ในระดับหลักการ State Hash สามารถใช้ตรวจว่าผู้เล่นจำลองสถานะเดียวกันหรือไม่ แต่ยังไม่มีหลักฐานยืนยันว่า Oriverse ใช้ Hash Tree, Per-tick Checksum หรือกลไกใดโดยเฉพาะ
3. Source Evidence: multiplayer_guidance → Core model ซึ่งระบุว่า Simulation State ตรวจสอบความสอดคล้องกันได้ รวมถึง Determinism caveats
4. API Contract: ยังไม่พบ Public API ที่ยืนยันได้สำหรับ GetStateHash, CompareStateHash หรือการอ่าน Desync Reports โดยตรง ชื่อเหล่านี้เป็นตัวอย่างความสามารถที่ต้องค้นเพิ่มเติม ไม่ใช่ API ของ Oriverse ที่ตรวจพบ
5. Working Example: สามารถใช้ Weave นับค่า State ที่คาดว่าจะเท่ากัน เช่นจำนวนครั้งที่ผู้เล่นใช้ประตู แล้วเปรียบเทียบ Logs ระหว่างการจำลอง แต่ไม่ถือว่าเทียบเท่าการตรวจ Hash ทั้ง World
6. Execution Trace: Not Disclosed สำหรับ State Hash Generation, Exchange, Comparison และ Recovery
7. Limits & Failure Modes: ความผิดพลาดจาก Object Spawn Ordering, Randomness หรือ Gameplay Logic ที่อาศัยข้อมูลนอก Deterministic Simulation อาจทำให้ผลลัพธ์ต่างกันได้ แต่ยังไม่มีข้อมูลยืนยันว่า Oriverse จัดการแต่ละกรณีอย่างไร
8. Verification: Expected: State เดียวกันควรให้ผลการตรวจความสอดคล้องตรงกัน; Actual: Not Run เพราะยังไม่มี State Hash Inspector ที่ตรวจพบ
9. Disclosure Status: Deterministic State Verification Partially Documented; State Hash Implementation Undisclosed
10. Research Gaps: Hash Function, Serialized State Schema, Validation Interval, Divergence Localization, Recovery Policy และ Replay Evidence
066 — Join, Leave, Reconnect และ Late Join จัดการอย่างไร?
1. Direct Answer: หัวข้อนี้มีรายละเอียดจากคู่มือค่อนข้างชัดเจน Oriverse สร้าง PlayerObject สำหรับผู้เล่นที่เข้าร่วม เมื่อหลุดการเชื่อมต่อจะยังเก็บ PlayerObject ไว้ประมาณ 90 วินาทีเพื่อเปิดโอกาสให้ Reconnect และเมื่อกลับมาในระยะเวลาดังกล่าวจะใช้ PlayerObject เดิม
ถ้ากลับมาหลังหมด Grace Period จะถือเป็น Fresh Spawn
2. Architecture: Player Join → Spawn PlayerObject → OnSpawned → Disconnect → OnPlayerLeft → Reconnect Grace → OnPlayerReconnected หรือ OnDestroy
3. Source Evidence: multiplayer_guidance → Players/teams; events → OnPlayerLeft/OnPlayerReconnected
4. API Contract:

067 — Server Authority และ Validation Boundary อยู่ตรงไหน?
1. Direct Answer: Oriverse ระบุว่า Client และ Server ประมวลผล Shared Deterministic Simulation แต่ไม่ได้เปิดเผยรูปแบบ Server Authority หรือ Trust Boundary อย่างละเอียด
ข้อควรระวังคือ การมี Server อยู่ในระบบไม่เพียงพอที่จะสรุปว่า Server ตรวจสอบทุก Gameplay Action แบบ Authoritative Server Architecture
2. Architecture: คู่มือยืนยันว่า Session Discovery เป็นบริการแยกจาก Gameplay Simulation โดย ListSessions() และ JoinSession() ไม่ได้สร้าง Replication Endpoint หรือเปลี่ยน Simulation Authority
3. Source Evidence: multiplayer_guidance → Core model, Session APIs
4. API Contract:
API เหล่านี้ใช้กับ Session Visibility/Discovery ไม่ใช่การกำหนดสิทธิ์แก้ Shared State
5. Working Example: ผู้เล่นสองคนสามารถแก้ Shared World State ผ่าน Weave Gameplay Logic ได้ตามกฎที่ผู้พัฒนาเขียน แต่ตัวอย่างนี้ไม่ใช่หลักฐานว่ามี Server-side Authorization สำหรับทุก Action
6. Execution Trace: Session Discovery → Join → Shared Deterministic Simulation โดยขั้นตอน Input Authentication และ Authority Verification ยังไม่เปิดเผย
7. Limits & Failure Modes: ไม่ควรใช้ UI Visibility หรือ Per-player Render Visibility เป็น Security Boundary เพราะคู่มือระบุว่า Private Rendering ไม่ได้ทำให้ข้อมูล Simulation เป็นความลับ
8. Verification: Expected: การแก้ข้อมูลที่ไม่มีสิทธิ์ควรถูกปฏิเสธโดย Security Boundary; Actual: Not Run และยังไม่มี API Contract ยืนยันจุดบังคับใช้สิทธิ์ดังกล่าว
9. Disclosure Status: Shared Simulation Model Documented; Server Authority / Validation Boundary Undisclosed
10. Research Gaps: Trust Model, Authoritative Input Validation, Anti-cheat Architecture, Host Permissions, State Ownership และ Secure Session Authentication
068 — Packet Loss, Latency, Jitter และ Cheating จัดการอย่างไร?
1. Direct Answer: คู่มือยืนยันว่าระบบมี Prediction และ Rollback ซึ่งเกี่ยวข้องกับการตอบสนองต่อข้อมูลที่มาถึงไม่พร้อมกัน แต่ไม่มีรายละเอียดการจัดการ Packet Loss, Jitter Buffer, Retransmission, Congestion Control หรือ Anti-cheat
2. Architecture: ระบบเกมที่ใช้ Deterministic Lockstep จำเป็นต้องควบคุมความสอดคล้องของ Input Stream แต่ไม่สามารถยืนยันว่าภายใน Oriverse ใช้ Reliable UDP, WebRTC DataChannel, WebSocket หรือ Transport แบบใด
3. Source Evidence: multiplayer_guidance → Core model, Determinism caveats
4. API Contract: ไม่พบ Public Network Impairment Controls หรือ Packet-level Telemetry API ในเอกสารที่ตรวจสอบ
5. Working Example: ไม่มี Working Example ระดับ Transport ที่ยืนยันได้จาก Weave API การใช้ playtest กับผู้เล่นจำลองทดสอบ Gameplay Events ได้ แต่ไม่ได้พิสูจน์การทำงานภายใต้ Packet Loss ของเครือข่ายจริง
6. Execution Trace: Undisclosed สำหรับ Packet Delivery, Acknowledgment, Loss Recovery และ Anti-cheat Enforcement
7. Limits & Failure Modes: Packet Loss สูงอาจทำให้ Input ล่าช้า แต่ระดับความรุนแรง ผลกระทบต่อ Frame Time และเงื่อนไข Disconnect ของ Oriverse ยังไม่ทราบ
8. Verification: Expected: เกมควรรักษาความสอดคล้องของ State ภายใต้ Network Impairment ที่ระบบรองรับ; Actual: Not Run
9. Disclosure Status: Prediction/Rollback Documented; Network Transport/Resilience/Security Undisclosed
10. Research Gaps: Network Protocol, RTT Measurement, Jitter Buffer, Resend Policy, Congestion Control, Lag Compensation และ Anti-cheat Validation
069 — รองรับผู้เล่นพร้อมกันสูงสุดเท่าไร?

2. Architecture: Players และ AI Players ต่างเป็น PlayerObject ใน Simulation โดย Bots สามารถใช้ #class player, Physics และ Animations ได้เช่นเดียวกัน แต่ไม่มี Human Viewer, Camera หรือ UI
3. Source Evidence: weave_coding → built_in_function_list → SpawnAIPlayer, multiplayer_guidance → AI players
4. API Contract:
ข้อจำกัดที่ระบุ: 64 Players รวม AI Players
