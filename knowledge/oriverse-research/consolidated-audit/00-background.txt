Weave Documentation: PASS
ยืนยันแล้วว่า Oriverse Editor เชื่อมต่อได้ และอ่านคู่มือ Weave ที่ก่อนหน้านี้ถูกปฏิเสธได้สำเร็จ โดย editor รายงาน build 05Oct26-23:23
นอกจากนี้ ผมอ่านโลกที่เปิดอยู่จริงแบบ Read-only ได้แล้ว พบว่าเป็นฉากชนบทเอเชียตะวันออกเฉียงใต้ มีทางเดิน บ้าน ต้นไม้ และองค์ประกอบภูมิทัศน์ รวม 46 บรรทัดของ Weave source
ข้อค้นพบทางเทคนิคสำคัญ:
* Weave เป็นภาษาสำหรับสร้างเกมจริง แบ่งเป็น scene declarations และ #class สำหรับ logic ที่ compile เป็น bytecode
* รองรับ procedural assets เช่น #mesh, #texture, #svg, #shader, #tree, #forest, #road_network, #particles และ #sound
* มีระบบ walker สำหรับ NPC จำนวนมาก และ crowd สำหรับตัวละครที่ต้องหลบหลีกสิ่งกีดขวาง
* ใช้ fixed-point arithmetic แบบ 48.16 เพื่อช่วยให้ผลการคำนวณ deterministic
* มีข้อจำกัดสำคัญคือ ไม่รองรับ recursive function calls
* ระบบ Asset Library มีการเปลี่ยน API: mesh_library_search ถูกแทนด้วย find_library_assets จึงต้อง refresh เครื่องมือก่อนทดสอบการค้นหา asset รุ่นใหม่
ฉากเดิมยังไม่ถูกเปลี่ยนแปลง การอ่านครั้งนี้ไม่ได้ลบหรือเขียนทับ draft

Oriverse สร้างเกมจาก Prompt อย่างไร ตั้งแต่คำสั่งจนเล่นได้จริง
จากกระบวนการที่เราใช้สร้าง KHOSAN–Oriverse Benchmark World v0.1 และคู่มือเครื่องมือของ Oriverse สามารถอธิบายได้ว่า ระบบไม่ได้สร้างเกมเป็นเพียงภาพ 3D แต่ใช้ AI แปลงความต้องการเป็น ซอร์สโค้ด Weave แล้วนำไป Compile, Simulation, Playtest และส่งเข้า Game Editor
Prompt-to-Playable Game Pipeline
ผังนี้เป็นการเรียบเรียง workflow จากเครื่องมือที่เปิดให้ใช้งาน ไม่ใช่การยืนยันว่า Oriverse มี AI Agents ภายในแยกเป็น 8 ตัวจริง
1. รับ Prompt และตีความความต้องการ
ตัวอย่างคำสั่งของเรา:
สร้างหมู่บ้านชนบทไทยแบบ 3D มีบ้านไม้ ถนน ทุ่งหญ้า NPC ร้านค้า Inventory และประตูที่ผู้เล่นสองคนใช้งานร่วมกัน
AI ต้องแปลงข้อความนี้เป็นข้อกำหนด เช่น จำนวนบ้าน ตำแหน่งวัตถุ รูปทรง ภูมิประเทศ วิธีควบคุมตัวละคร กฎการซื้อสินค้า และสิ่งที่ต้องแชร์ระหว่างผู้เล่น
ขั้นตอนตีความนี้ดำเนินการโดย AI ที่เรียกใช้ Oriverse ไม่ใช่หลักฐานว่า Oriverse มีระบบ Requirement Parser อัตโนมัติแยกต่างหาก
2. อ่านคู่มือและเลือกเทคนิคสร้างเกม
AI อ่านคู่มือผ่าน read_skill โดยเลือกเฉพาะส่วนที่จำเป็น เช่น weave_coding, mesh_dsl, terrain_generation และ ui_patterns
จากนั้นตัดสินใจว่าจะใช้เครื่องมือใดสร้างองค์ประกอบแต่ละประเภท:

	3. สร้าง Weave World Description
นี่คือหัวใจของการทำงาน
Weave เป็นภาษาสำหรับกำหนดทั้ง สิ่งที่มีอยู่ในโลก และ พฤติกรรมของสิ่งเหล่านั้น
ตัวอย่างย่อ:


#mesh VillageHouse
  // สร้างโครงสร้างบ้าน
#end


object HouseA {
  model = "mesh.VillageHouse"
  position = (0, 1000, 0)
}


#class DoorLogic
var Open = false


func Toggle() {
  Open = not Open
}
#end


ระบบจึงไม่ได้อาศัยภาพที่ AI วาดไว้เท่านั้น แต่มีข้อมูล object, position, geometry, collision, state และ gameplay logic ที่ Engine สามารถนำไปทำงานต่อได้
4. Compile และตรวจสอบความถูกต้อง
เมื่อสร้างซอร์สโค้ดแล้ว จะใช้ stage_new_world หรือ patch_and_run_pending_world เพื่อตรวจสอบโค้ดและจำลองเฟรมเริ่มต้น
ถ้าพบข้อผิดพลาด เช่น ชื่อฟังก์ชันไม่ถูกต้อง ชนิดข้อมูลไม่ตรง หรือใช้ Mesh DSL ผิด AI สามารถอ่าน diagnostics แล้วแก้ไขเฉพาะส่วนที่ผิด ก่อนทดสอบใหม่
ใน Benchmark ของเราเกิดเหตุการณ์จริง เช่น:
* Compiler พบว่าการกำหนด Owner ต้อง cast ชนิดเป็น player
* Mesh compiler พบว่า box_at ไม่รับ argument ชื่อ position
* หลังแก้ไขทั้งสองจุด จึงผ่าน Compile
* Revision 7 ผ่านการจำลอง 60 frames โดยใช้เวลาตรวจสอบประมาณ 34 ms
เวลานี้เป็น ระยะเวลาตรวจสอบในสภาพแวดล้อมทดสอบ ไม่ใช่เวลาโหลดเกมจริงหรือค่า FPS ของผู้เล่น
5. Simulation: ตรวจว่าระบบเกมทำงานจริงหรือไม่
หลัง Compile ผ่าน จะใช้ระบบจำลองเกมตรวจสอบพฤติกรรมต่าง ๆ เช่น ผู้เล่นเกิดถูกตำแหน่งหรือไม่ เงินลดเมื่อซื้อสินค้าหรือไม่ และประตูเปลี่ยนสถานะได้จริงหรือไม่
สำหรับ Multiplayer คู่มือ Oriverse ระบุว่าใช้แนวทาง Deterministic Lockstep พร้อม Client Prediction และ Rollback กล่าวคือ ผู้เข้าร่วมจำลองสถานะเกมร่วมกันจากข้อมูลและอินพุตที่สอดคล้องกัน ไม่ใช่ระบบที่ต้องเขียนการส่งสถานะวัตถุทุกชิ้นผ่านเครือข่ายเอง
ใน Benchmark เรากำหนดให้:
* Coins และ Inventory เป็นสถานะแยกของผู้เล่นแต่ละคน
* ประตูเป็นสถานะร่วมกันของโลก
* ปุ่มใน HUD ต้องตรวจว่าใครเป็นผู้กด
* การซื้อชาต้องตรวจเงิน พื้นที่ใกล้ร้าน และช่องว่างใน Inventory

7. ส่งเกมเข้า Oriverse Editor
เมื่อพร้อมส่งมอบ ใช้ submit_pending_world ส่งเวอร์ชันที่ผ่านการตรวจไปยัง Editor

จากนั้นสามารถบันทึกเป็น Project, สร้าง Share Link หรือ Publish เป็นเกมสาธารณะได้ตามสิทธิ์และเงื่อนไขของแต่ละเครื่องมือ

จากคู่มือ weave_coding ที่ผมอ่านผ่าน Oriverse โดยตรง Weave คือภาษาเฉพาะทางสำหรับพัฒนาเกม (Game Domain-Specific Language หรือ Game DSL) ซึ่งสามารถอธิบายฉาก 3D, สร้าง Assets, เขียนกฎเกม และควบคุมพฤติกรรมของวัตถุภายในโลกเดียวกันได้
สิ่งสำคัญคือ Weave ไม่ใช่ตัว AI ที่เข้าใจ Prompt แต่เป็นภาษาที่ AI ใช้สั่งงาน Game Engine
เพื่อให้เข้าใจระบบทั้งหมด ต้องแยกออกเป็นสามส่วน:
1. AI Authoring — ทำความเข้าใจความต้องการและเขียน Weave
2. Weave Compiler & Runtime — แปลโค้ดและประมวลผลกฎเกม
3. Oriverse Engine — จัดการกราฟิก ฟิสิกส์ อินพุต เสียง และ Multiplayer
1. สถาปัตยกรรมการทำงานของ Weave
ผังเชิงแนวคิดจาก API และเอกสาร Weave ไม่ได้อ้างว่าเป็นรายละเอียดโครงสร้างภายในของ Compiler ที่เปิดเผยครบทุกโมดูล
2. Weave มีส่วนประกอบอะไรบ้าง
ส่วนประกอบ

3. Weave ทำงานอย่างไรในหนึ่ง Frame
หัวข้อนี้เป็นหัวใจของ Runtime และเป็นรายละเอียดที่คู่มือ Oriverse ระบุไว้ชัดเจน
1
Spawn Phase
เรียก OnPreSpawn ให้ object ใหม่ก่อน จากนั้นจึงเข้าสู่ OnSpawned
2
Event Dispatch
ประมวลผล Update, อินพุต, เมาส์ และ UI actions
3
Motion / Physics
ประยุกต์คำสั่งการเคลื่อนที่ ความเร็ว แรงโน้มถ่วง และการกระโดด
4
Collision & Regions
คำนวณการสัมผัสและการเข้าสู่เขตจากตำแหน่งหลัง Physics
5
State for Next Tick
ตำแหน่งหลัง Physics จะถูกอ่านได้จาก Script ใน Tick ถัดไป
มีรายละเอียดที่นักพัฒนาเกมต้องเข้าใจ เช่น:
* GetPosition() ที่อ่านภายใน Tick จะได้ตำแหน่งก่อน Physics ของ Tick นั้น
* คำสั่งเคลื่อนที่แบบ Continuously ต้องเรียกทุก Frame และคำสั่งล่าสุดในประเภทเดียวกันเป็นตัวที่ใช้จริง
* TeleportTo() มีลำดับความสำคัญเหนือการเคลื่อนที่แบบต่อเนื่องภายใน Tick เดียวกัน
* ไม่ควรสมมติว่า OnSpawned ของ Object ต่าง ๆ จะเรียงตามลำดับที่ประกาศไว้ในซอร์ส
สิ่งเหล่านี้ทำให้การเขียน Weave ต้องอาศัยความเข้าใจ Execution Model ไม่ใช่เพียงจำชื่อฟังก์ชัน
4. Weave สร้างโมเดลและกราฟิกได้อย่างไร
Weave ไม่ได้สร้างทุกอย่างโดยใช้ AI Image Generation
ตัวอย่างเช่น #mesh สามารถสร้างรูปทรงจากคำสั่งเรขาคณิต แล้ว bake ออกมาเป็น Mesh ที่มี vertices, triangles และ material slots
#texture ใช้คำสั่งสร้างค่าพื้นผิว เช่น albedo, normal และ ORM (Occlusion, Roughness, Metallic) โดยประมวลผลเป็น Texture Maps
#terrain สามารถสร้างภูเขา เนิน ที่ราบ และทางน้ำด้วยการคำนวณแบบ procedural
จึงมีความแตกต่างระหว่าง:
* Procedural Generation: สร้างจากสูตรและข้อมูลที่กำหนด
* Generative AI: ใช้โมเดล AI สังเคราะห์ภาพหรือ Asset
* Library Reuse: เลือก Asset ที่มีอยู่แล้วมาใช้งาน
Oriverse รองรับแนวทางเหล่านี้ผ่านเครื่องมือคนละชุด
5. ระบบ Multiplayer ของ Weave
จุดที่น่าสนใจมากคือ Oriverse ระบุการใช้ Deterministic Lockstep + Client Prediction + Rollback
ตามเอกสาร แนวทางนี้ทำให้ทุกผู้เข้าร่วมจำลองสถานะโลกจากโค้ดและอินพุตที่สอดคล้องกัน โดยไม่จำเป็นต้องเขียนระบบส่งตำแหน่งและสถานะของทุก Object เอง
ตัวอย่างจาก Benchmark ของเรา:
Player 1
  Coins = 40
  Inventory = Rice x2


Player 2
  Coins = 40
  Inventory = Rice x2


Shared World
  Door.Open = false
หาก Player 1 กดเปิดประตู ฟังก์ชัน Toggle() จะแก้สถานะร่วมกันเป็น true และกลไก Multiplayer จะทำให้ผู้เล่นที่อยู่ใน Simulation เดียวกันมีผลลัพธ์สอดคล้องกัน
อย่างไรก็ตาม การทดสอบสองผู้เล่นบนเครื่องมือจำลองยังไม่เทียบเท่าการรับรองระบบเครือข่ายภายใต้ Packet Loss, Latency หรือการเชื่อมต่ออินเทอร์เน็ตจริง
6. แล้ว AI เข้าใจระบบ Weave ทั้งหมดได้อย่างไร
คำตอบคือ AI ไม่ได้รู้จักทุก API อย่างถูกต้องจากความจำโดยอัตโนมัติ
ในกระบวนการที่ตรวจสอบได้ AI ใช้แหล่งข้อมูลหลายส่วนประกอบกัน:
1. Language Reference — กฎไวยากรณ์ ชนิดข้อมูล และคำสั่งที่รองรับ
2. API Signatures — รับ parameter อะไร คืนค่าอะไร และเรียกบน Object ประเภทใด
3. Usage Examples — รูปแบบการเขียน Inventory, NPC, Terrain และ Multiplayer
4. Existing World Source — อ่านโค้ดจริงที่อยู่ในโปรเจกต์
5. Compiler Diagnostics — ใช้ข้อผิดพลาดจาก Compiler แก้ความเข้าใจที่ไม่ถูกต้อง
6. Runtime Evidence — ใช้ Simulation และ Playtest ตรวจว่าการทำงานตรงตามเจตนาหรือไม่
ตัวอย่างจริงจาก Benchmark: AI เขียนชื่อ argument ของ box_at ผิด แล้ว Compiler ระบุ argument ที่ยอมรับได้ จากนั้น AI แก้โค้ดและ Compile ผ่าน นี่คือตัวอย่างของ Documentation-Grounded Coding + Compiler Feedback Loop
ความรู้ที่ AI ใช้จึงไม่ใช่การอ่านฐานข้อมูลทั้งหมดเข้าไปพร้อมกัน แต่เป็นการค้นเฉพาะเอกสารที่สัมพันธ์กับงาน แล้วอาศัย Compiler และ Runtime เป็นตัวตรวจสอบ
7. สิ่งที่ยังต้องศึกษาเพิ่ม หากต้องการเข้าใจ Weave ระดับสร้าง Engine เอง

1. MCP คืออะไรในระบบนี้
MCP หรือ Model Context Protocol ไม่ใช่ AI model และไม่ใช่ game engine
มันเป็นเหมือน มาตรฐานสายสื่อสารระหว่าง AI กับ software/tool
สมมติผมพูดกับ Oriverse ว่า:
“สร้างบ้านไม้ชนบทตามภาพนี้ไว้ด้านซ้ายของถนน”
ตัว LLM ไม่ได้เอามือไปขยับ object ใน editor โดยตรง
มันเปลี่ยนความตั้งใจนั้นเป็นการเรียกเครื่องมือ เช่นแนวคิดประมาณ:
LLM
 ↓


MCP request


tool = attach_reference_image(...)
tool = find_assets(...)
tool = patch_and_run_pending_world(...)
tool = playtest(...)


 ↓


Oriverse Editor
MCP ทำหน้าที่หลักประมาณนี้:
WHO
  agent/session ไหน


WHERE
  editor ไหน


WHAT
  tool ไหน


INPUT
  parameters อะไร


OUTPUT
  result / error / evidence / revision
ตัว connector ที่ผมตรวจในแชตนี้มี Oriverse editor session จริง และมี agent/session ถูก pin เข้ากับ editor โดยตรง
ดังนั้นมันใกล้กับ:
AI → API/RPC → Editor
มากกว่า:
AI → กด mouse มั่ว ๆ บนหน้าจอ

Weave Documentation: PASS
ยืนยันแล้วว่า Oriverse Editor เชื่อมต่อได้ และอ่านคู่มือ Weave ที่ก่อนหน้านี้ถูกปฏิเสธได้สำเร็จ โดย editor รายงาน build 05Oct26-23:23
นอกจากนี้ ผมอ่านโลกที่เปิดอยู่จริงแบบ Read-only ได้แล้ว พบว่าเป็นฉากชนบทเอเชียตะวันออกเฉียงใต้ มีทางเดิน บ้าน ต้นไม้ และองค์ประกอบภูมิทัศน์ รวม 46 บรรทัดของ Weave source
ข้อค้นพบทางเทคนิคสำคัญ:
* Weave เป็นภาษาสำหรับสร้างเกมจริง แบ่งเป็น scene declarations และ #class สำหรับ logic ที่ compile เป็น bytecode
* รองรับ procedural assets เช่น #mesh, #texture, #svg, #shader, #tree, #forest, #road_network, #particles และ #sound
* มีระบบ walker สำหรับ NPC จำนวนมาก และ crowd สำหรับตัวละครที่ต้องหลบหลีกสิ่งกีดขวาง
* ใช้ fixed-point arithmetic แบบ 48.16 เพื่อช่วยให้ผลการคำนวณ deterministic

Prompt-to-Playable Game Pipeline
ผังนี้เป็นการเรียบเรียง workflow จากเครื่องมือที่เปิดให้ใช้งาน ไม่ใช่การยืนยันว่า Oriverse มี AI Agents ภายในแยกเป็น 8 ตัวจริง
1. รับ Prompt และตีความความต้องการ
ตัวอย่างคำสั่งของเรา:
สร้างหมู่บ้านชนบทไทยแบบ 3D มีบ้านไม้ ถนน ทุ่งหญ้า NPC ร้านค้า Inventory และประตูที่ผู้เล่นสองคนใช้งานร่วมกัน
AI ต้องแปลงข้อความนี้เป็นข้อกำหนด เช่น จำนวนบ้าน ตำแหน่งวัตถุ รูปทรง ภูมิประเทศ วิธีควบคุมตัวละคร กฎการซื้อสินค้า และสิ่งที่ต้องแชร์ระหว่างผู้เล่น
ขั้นตอนตีความนี้ดำเนินการโดย AI ที่เรียกใช้ Oriverse ไม่ใช่หลักฐานว่า Oriverse มีระบบ Requirement Parser อัตโนมัติแยกต่างหาก

4. Compile และตรวจสอบความถูกต้อง
เมื่อสร้างซอร์สโค้ดแล้ว จะใช้ stage_new_world หรือ patch_and_run_pending_world เพื่อตรวจสอบโค้ดและจำลองเฟรมเริ่มต้น
ถ้าพบข้อผิดพลาด เช่น ชื่อฟังก์ชันไม่ถูกต้อง ชนิดข้อมูลไม่ตรง หรือใช้ Mesh DSL ผิด AI สามารถอ่าน diagnostics แล้วแก้ไขเฉพาะส่วนที่ผิด ก่อนทดสอบใหม่
ใน Benchmark ของเราเกิดเหตุการณ์จริง เช่น:
* Compiler พบว่าการกำหนด Owner ต้อง cast ชนิดเป็น player
* Mesh compiler พบว่า box_at ไม่รับ argument ชื่อ position
* หลังแก้ไขทั้งสองจุด จึงผ่าน Compile
* Revision 7 ผ่านการจำลอง 60 frames โดยใช้เวลาตรวจสอบประมาณ 34 ms
เวลานี้เป็น ระยะเวลาตรวจสอบในสภาพแวดล้อมทดสอบ ไม่ใช่เวลาโหลดเกมจริงหรือค่า FPS ของผู้เล่น
5. Simulation: ตรวจว่าระบบเกมทำงานจริงหรือไม่
หลัง Compile ผ่าน จะใช้ระบบจำลองเกมตรวจสอบพฤติกรรมต่าง ๆ เช่น ผู้เล่นเกิดถูกตำแหน่งหรือไม่ เงินลดเมื่อซื้อสินค้าหรือไม่ และประตูเปลี่ยนสถานะได้จริงหรือไม่
สำหรับ Multiplayer คู่มือ Oriverse ระบุว่าใช้แนวทาง Deterministic Lockstep พร้อม Client Prediction และ Rollback กล่าวคือ ผู้เข้าร่วมจำลองสถานะเกมร่วมกันจากข้อมูลและอินพุตที่สอดคล้องกัน ไม่ใช่ระบบที่ต้องเขียนการส่งสถานะวัตถุทุกชิ้นผ่านเครือข่ายเอง
ใน Benchmark เรากำหนดให้:
* Coins และ Inventory เป็นสถานะแยกของผู้เล่นแต่ละคน
* ประตูเป็นสถานะร่วมกันของโลก
* ปุ่มใน HUD ต้องตรวจว่าใครเป็นผู้กด
* การซื้อชาต้องตรวจเงิน พื้นที่ใกล้ร้าน และช่องว่างใน Inventory

ทำความเข้าใจ Weave Engine ของ Oriverse ตั้งแต่ภาษาโปรแกรมจนถึงการทำงานของเกมทั้งหมด
จากคู่มือ weave_coding ที่ผมอ่านผ่าน Oriverse โดยตรง Weave คือภาษาเฉพาะทางสำหรับพัฒนาเกม (Game Domain-Specific Language หรือ Game DSL) ซึ่งสามารถอธิบายฉาก 3D, สร้าง Assets, เขียนกฎเกม และควบคุมพฤติกรรมของวัตถุภายในโลกเดียวกันได้
สิ่งสำคัญคือ Weave ไม่ใช่ตัว AI ที่เข้าใจ Prompt แต่เป็นภาษาที่ AI ใช้สั่งงาน Game Engine
เพื่อให้เข้าใจระบบทั้งหมด ต้องแยกออกเป็นสามส่วน:
1. AI Authoring — ทำความเข้าใจความต้องการและเขียน Weave
2. Weave Compiler & Runtime — แปลโค้ดและประมวลผลกฎเกม
3. Oriverse Engine — จัดการกราฟิก ฟิสิกส์ อินพุต เสียง และ Multiplayer
1. สถาปัตยกรรมการทำงานของ Weave
ผังเชิงแนวคิดจาก API และเอกสาร Weave ไม่ได้อ้างว่าเป็นรายละเอียดโครงสร้างภายในของ Compiler ที่เปิดเผยครบทุกโมดูล

3. Weave ทำงานอย่างไรในหนึ่ง Frame
หัวข้อนี้เป็นหัวใจของ Runtime และเป็นรายละเอียดที่คู่มือ Oriverse ระบุไว้ชัดเจน
มีรายละเอียดที่นักพัฒนาเกมต้องเข้าใจ เช่น:
* GetPosition() ที่อ่านภายใน Tick จะได้ตำแหน่งก่อน Physics ของ Tick นั้น
* คำสั่งเคลื่อนที่แบบ Continuously ต้องเรียกทุก Frame และคำสั่งล่าสุดในประเภทเดียวกันเป็นตัวที่ใช้จริง
* TeleportTo() มีลำดับความสำคัญเหนือการเคลื่อนที่แบบต่อเนื่องภายใน Tick เดียวกัน
* ไม่ควรสมมติว่า OnSpawned ของ Object ต่าง ๆ จะเรียงตามลำดับที่ประกาศไว้ในซอร์ส
สิ่งเหล่านี้ทำให้การเขียน Weave ต้องอาศัยความเข้าใจ Execution Model ไม่ใช่เพียงจำชื่อฟังก์ชัน
4. Weave สร้างโมเดลและกราฟิกได้อย่างไร
Weave ไม่ได้สร้างทุกอย่างโดยใช้ AI Image Generation
ตัวอย่างเช่น #mesh สามารถสร้างรูปทรงจากคำสั่งเรขาคณิต แล้ว bake ออกมาเป็น Mesh ที่มี vertices, triangles และ material slots
#texture ใช้คำสั่งสร้างค่าพื้นผิว เช่น albedo, normal และ ORM (Occlusion, Roughness, Metallic) โดยประมวลผลเป็น Texture Maps
#terrain สามารถสร้างภูเขา เนิน ที่ราบ และทางน้ำด้วยการคำนวณแบบ procedural
จึงมีความแตกต่างระหว่าง:
* Procedural Generation: สร้างจากสูตรและข้อมูลที่กำหนด
* Generative AI: ใช้โมเดล AI สังเคราะห์ภาพหรือ Asset
* Library Reuse: เลือก Asset ที่มีอยู่แล้วมาใช้งาน
Oriverse รองรับแนวทางเหล่านี้ผ่านเครื่องมือคนละชุด
5. ระบบ Multiplayer ของ Weave
จุดที่น่าสนใจมากคือ Oriverse ระบุการใช้ Deterministic Lockstep + Client Prediction + Rollback
ตามเอกสาร แนวทางนี้ทำให้ทุกผู้เข้าร่วมจำลองสถานะโลกจากโค้ดและอินพุตที่สอดคล้องกัน โดยไม่จำเป็นต้องเขียนระบบส่งตำแหน่งและสถานะของทุก Object เอง
ตัวอย่างจาก Benchmark ของเรา:
หาก Player 1 กดเปิดประตู ฟังก์ชัน Toggle() จะแก้สถานะร่วมกันเป็น true และกลไก Multiplayer จะทำให้ผู้เล่นที่อยู่ใน Simulation เดียวกันมีผลลัพธ์สอดคล้องกัน
อย่างไรก็ตาม การทดสอบสองผู้เล่นบนเครื่องมือจำลองยังไม่เทียบเท่าการรับรองระบบเครือข่ายภายใต้ Packet Loss, Latency หรือการเชื่อมต่ออินเทอร์เน็ตจริง
6. แล้ว AI เข้าใจระบบ Weave ทั้งหมดได้อย่างไร
คำตอบคือ AI ไม่ได้รู้จักทุก API อย่างถูกต้องจากความจำโดยอัตโนมัติ
ในกระบวนการที่ตรวจสอบได้ AI ใช้แหล่งข้อมูลหลายส่วนประกอบกัน:
1. Language Reference — กฎไวยากรณ์ ชนิดข้อมูล และคำสั่งที่รองรับ
2. API Signatures — รับ parameter อะไร คืนค่าอะไร และเรียกบน Object ประเภทใด
3. Usage Examples — รูปแบบการเขียน Inventory, NPC, Terrain และ Multiplayer
4. Existing World Source — อ่านโค้ดจริงที่อยู่ในโปรเจกต์
5. Compiler Diagnostics — ใช้ข้อผิดพลาดจาก Compiler แก้ความเข้าใจที่ไม่ถูกต้อง
6. Runtime Evidence — ใช้ Simulation และ Playtest ตรวจว่าการทำงานตรงตามเจตนาหรือไม่
ตัวอย่างจริงจาก Benchmark: AI เขียนชื่อ argument ของ box_at ผิด แล้ว Compiler ระบุ argument ที่ยอมรับได้ จากนั้น AI แก้โค้ดและ Compile ผ่าน นี่คือตัวอย่างของ Documentation-Grounded Coding + Compiler Feedback Loop
ความรู้ที่ AI ใช้จึงไม่ใช่การอ่านฐานข้อมูลทั้งหมดเข้าไปพร้อมกัน แต่เป็นการค้นเฉพาะเอกสารที่สัมพันธ์กับงาน แล้วอาศัย Compiler และ Runtime เป็นตัวตรวจสอบ
7. สิ่งที่ยังต้องศึกษาเพิ่ม หากต้องการเข้าใจ Weave ระดับสร้าง Engine เอง
ประเด็น
	สิ่งที่เราทราบ
	สิ่งที่ยังไม่ยืนยัน
	Compiler
	มีการ Compile class เป็น bytecode
	รูปแบบ bytecode และ instruction set
	Type System
	ตรวจชนิดข้อมูลและการ cast
	รายละเอียดระบบ type checking ภายในทั้งหมด
	VM / Runtime
	มี Tick, Events, State และ Scheduling
	การจัดหน่วยความจำและกลไก VM ระดับลึก
	Determinism
	ใช้ fixed-point 48.16 และ Lockstep
	โปรโตคอลเครือข่ายและ State Hash ภายใน
	Rendering
	รองรับ PBR, Shadows และ WGSL hooks
	โครงสร้าง Render Graph ทั้งหมด
	Physics
	มี Collision, Kinematic และ Dynamic Bodies
	Algorithm ฟิสิกส์และ Solver ทั้งหมด
	Assets
	มี procedural mesh/texture/terrain
	Binary Asset Format และ Export ABI ทั้งหมด
	ต้องแยกให้ชัดว่า การอ่านคู่มือสำหรับผู้เขียนเกม ไม่เท่ากับการเข้าถึง Source Code ภายในของ Game Engine

ถ้า KHOSAN Studio จะสร้างระบบลักษณะเดียวกับ Weave
แนวทางที่เหมาะสมคือสร้างภาษาเกมกลางของเราเอง เช่น KHOSAN Game IR แล้วให้ AI แปลง Prompt เป็นข้อมูลที่มีโครงสร้าง ตรวจ Schema และส่งต่อไปยัง Game Runtime
ตัวอย่างแนวคิด:
ข้อสรุปสำคัญ: สิ่งที่ทำให้ Weave มีประโยชน์ต่อ AI ไม่ใช่เพียงการเป็นภาษาเขียนเกม แต่คือการกำหนดสัญญาที่ชัดเจนระหว่าง ความต้องการของมนุษย์ → โค้ด → สถานะเกม → ผลลัพธ์ที่ตรวจสอบได้
ถ้าเราจะศึกษาเพื่อสร้าง KHOSAN Studio จริง ผมเห็นว่าควรลงลึกต่อในสามเรื่องคือ Weave Language Specification, Execution/State Model และ Compiler–Runtime Contract เพราะเป็นสามส่วนที่ทำให้ระบบสร้างเกมจาก Prompt สามารถพัฒนาต่อยอด ทดสอบซ้ำ และควบคุมคุณภาพได้อย่างเป็นระบบ
