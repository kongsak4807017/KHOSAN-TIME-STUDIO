101 — #terrain ประกอบ Heightfield จากสูตรและ Features อย่างไร?
1. Direct Answer: #terrain Name ... #end เป็น Procedural Recipe ที่นิยาม Relief, Erosion, Noise, Landforms และ Sparse Features แล้วสร้าง Terrain ด้วย SpawnTerrainRecipe(...) โดยคู่มือระบุว่า Recipe ถูกประเมินจากโปรแกรมแบบ Fixed-point ไม่ต้องสร้าง Height Raster ทั้งโลกเก็บไว้ใน Simulation State
2. Architecture: Terrain ประกอบด้วย Base Landform, Named Features, Erosion, Noise/Channel Modifiers และ Gameplay Flattening ตามลำดับการประมวลผลที่คู่มือกำหนด
3. Source Evidence: weave_coding → terrain_generation, terrain_generation → Recipes

102 — Noise, Erosion และ Terrain Feature Evaluation ทำงานอย่างไร?
1. Direct Answer: Oriverse รองรับ Procedural Noise หลายประเภท รวมถึงระบบ Erosion ที่ชื่อ OriErosion และการประมวลผล Heightfield ผ่าน Functions กลุ่ม TerrainHeights*
2. Architecture: สำหรับ Recipe: Base Noise/Landforms → Erosion → Channel/Detail → Flatten/Carve ตาม Authoring Rules ส่วน Heightfield ใช้ลำดับ Operation บน Grid ที่ผู้เขียนกำหนด
3. Source Evidence: weave_coding → terrain_generation; terrain_generation → Heightfield workflow
4. API Contract: Noise Functions ได้แก่ Hash2, ValueNoise2, Fbm2, Ridged2, Billow2, Voronoi2 ซึ่งเป็น Pure Deterministic Functions ตามคู่มือ
Heightfield Operations ได้แก่ TerrainHeightsNoise, TerrainHeightsAddNoise, TerrainHeightsWarp, TerrainHeightsThermalErode, TerrainHeightsHydraulicErode, TerrainHeightsSmooth และ TerrainHeightsRemapCurve
5. Working Example — จากคู่มือ:
นี่เป็น Code Fragment สำหรับสร้างเนินทราย ไม่ใช่ World ที่ Compile ผ่านแล้ว
6. Execution Trace: Initialize Height List → Generate Base Noise → Apply Smoothing/Erosion → Apply Remapping → Apply Final Gameplay Flats → Spawn Terrain
7. Limits & Failure Modes: TerrainHeights* ทำงานบน List ขนาด SamplesX × SamplesY และ Error เมื่อขนาด List ผิด โดย Hydraulic Erosion เป็น Iterative CPU Operation ที่อาจมีต้นทุนสูง
8. Verification: Expected: Noise สร้าง Relief, Erosion ทำให้ลักษณะภูมิประเทศเปลี่ยน; Actual: Not Run
9. Disclosure Status: Public Operations Documented; Internal Erosion Equations Partially Undisclosed
10. Research Gaps: OriErosion Mathematical Specification, Numerical Stability, Iteration Costs, Flow Accumulation และ Reproducibility Benchmarks
103 — Terrain Collision ตรงกับ Rendered Terrain อย่างไร?
1. Direct Answer: สำหรับ Procedural Recipe คู่มือระบุว่า Flatten และ Carve Effects มีผลทั้ง Collision และ Rendering อย่างสอดคล้องกันตลอดพื้นที่ที่รองรับ แต่กรณี Hybrid Heightfield มีข้อแตกต่าง คือ Display Extension สามารถแสดงภูมิประเทศไกลเกิน Bounded Collision Grid ได้
2. Architecture: Recipe Terrain ใช้ Procedural Field สำหรับ Ground Evaluation ส่วน Bounded Heightfield ใช้ Quantized Grid และ Collision ที่สัมพันธ์กับ Grid ขนาดจำกัด
3. Source Evidence: weave_coding → terrain_generation; terrain_generation → Hybrid Lane
4. API Contract:
GroundHeightAtXY คืน World Z ในหน่วยเซนติเมตรของ Ground/Static Collider สูงสุดที่พิกัด XY
5. Working Example:
6. Execution Trace: Query XY → Evaluate Terrain/Static Ground → Return Height → Spawn/Place Object at Surface
7. Limits & Failure Modes: SetTerrainDisplayExtension(radiusM) ขยายเฉพาะภาพ Rendering โดยไม่ได้ขยาย Grid Collision หรือ Grid Edits ดังนั้นบริเวณที่มองเห็นอาจไม่ใช่บริเวณที่เดินหรือแก้ไขได้
8. Verification: Expected: Terrain Recipe Ground Query ตรงกับพื้นหลังการ Flatten/Carve; Actual: คู่มือระบุ Contract ดังกล่าว แต่ยังไม่ได้ตรวจด้วย Ground Sample Matrix ในรอบนี้
9. Disclosure Status: Public Collision/Display Semantics Documented; Exact Mesh-vs-Collider Error Bounds Undisclosed
10. Research Gaps: Maximum Vertical Error, Collision Sampling Resolution, GPU Tessellation Differences และ Edge Behavior
104 — Coordinate System และ Precision ของ Terrain
1. Direct Answer: Weave ใช้ World Coordinates แบบ Z-up ในหน่วยเซนติเมตร ส่วน Terrain Recipe Feature Coordinates ใช้ Terrain-local Meters และ Bounded Heightfield ใช้ Cell Coordinates กับ Sample Heights ในหน่วยเซนติเมตร
2. Architecture: Terrain Instance Transform แปลง Local Coordinates ไปเป็น World Coordinates ขณะที่ Heightfield จัดเก็บ Samples แบบ Row-major และมี Origin อยู่กึ่งกลาง Grid
3. Source Evidence: weave_coding → terrain_generation, procedural_generation
4. API Contract:
ตำแหน่งของ Heightfield Cell:
X=Px+(ix−Sx−12)CX=P_x+\left(i_x-\frac{S_x-1}{2}\right)C Y=Py+(iy−Sy−12)CY=P_y+\left(i_y-\frac{S_y-1}{2}\right)C
โดย PP คือ Terrain Position, Sx,SyS_x,S_y คือจำนวน Samples และ CC คือ Cell Size (cm)
ค่าความสูงของ Bounded Heightfield ถูก Quantize เป็น u16 โดยความละเอียดต่อระดับประมาณ:
Δh=hmax⁡−hmin⁡65535\Delta h=\frac{h_{\max}-h_{\min}}{65535}
5. Working Example: Heightfield ขนาด 257×257 ที่ Cell Size 200 cm มีระยะระหว่าง Sample แรกกับ Sample สุดท้ายเท่ากับ 512 m ต่อแกน ตามสูตรพิกัดจากคู่มือ
6. Execution Trace: Grid Index → Convert to Local XY → Add Terrain Origin → Evaluate/Interpolate Height → Return World Position
7. Limits & Failure Modes: ความสูงสุดโต่งเพียงจุดเดียวอาจขยาย Quantization Range ทำให้ Precision ของพื้นที่อื่นลดลง
8. Verification: Expected: Coordinates และ Quantization ตรงตามสูตร; Actual: อ้างอิงคู่มือ ยังไม่ได้วัด Numeric Error จริง
9. Disclosure Status: Documented
10. Research Gaps: Interpolation Precision, Origin Shifting, Large-coordinate Numerical Stability และ Cross-platform Height Sampling
105 — สร้างถนน แม่น้ำ และพื้นที่ราบด้วยวิธีใด?

2. Architecture: ควรแยก Terrain Shaping ออกจาก Road/Water Rendering เพราะการขุดร่องใน Terrain ไม่ได้สร้างน้ำหรือผิวถนนโดยอัตโนมัติ

106 — Vegetation Scattering และ Biome Rules
1. Direct Answer: Oriverse รองรับ #forest, #scatter และ Terrain Grass ซึ่งวางพืชตาม Ground Height, Slope, Elevation Bands และ Mask Conditions ได้
อย่างไรก็ตาม ยังไม่พบ Biome Graph Schema กลางที่บังคับให้ผู้พัฒนานิยาม Biome ทุกประเภทผ่านระบบเดียว
2. Architecture: Terrain สร้าง Height/Slope Field → Forest/Scatter Recipe ใช้ Filtering Conditions → Engine วาง Vegetation Instances → Rendering ใช้ LOD/Culling ตามระบบที่รองรับ
3. Source Evidence: weave_coding → forest_dsl_usage, scatter_dsl_usage, procedural_generation
4. API Contract:
#forest ใช้ species, spacing, density_pct, height_min_cm, height_max_cm และ slope_max_pct
#scatter เพิ่มความสามารถ เช่น splat_mask_min_pct, splat_mask_max_pct, terrain_normal_align_pct และ shape
5. Working Example — จากรูปแบบที่คู่มือรองรับ:
ตัวอย่างนี้ต้องมี #tree Pine อยู่ใน World เดียวกันก่อน จึงไม่ถือว่าเป็น Standalone Program ที่ผ่าน Compiler แล้ว
6. Execution Trace: Evaluate Terrain Height → Check Region Z Span → Check Slope/Elevation → Deterministic Placement → Create Display/Trunk Colliders ตามชนิด Vegetation
7. Limits & Failure Modes: หนึ่ง Forest Region มีเพดาน 16,384 Trees และการกระจายต้นไม้มากเกินจะถูกลดจำนวนเพื่ออยู่ใน Budget
8. Verification: Expected: ต้นไม้ไม่ถูกวางบนพื้นที่สูง/ลาดเกินเงื่อนไข; Actual: Not Run
9. Disclosure Status: Forest/Scatter Filters Documented; Unified Biome System Undisclosed
10. Research Gaps: Biome Transition Blending, Ecosystem State, Seasonal Changes, Climate Simulation และ Vegetation Memory Residency
107 — Terrain LOD และ Chunk Streaming ทำงานอย่างไร?
1. Direct Answer: เอกสารยืนยันว่า SpawnTerrainRecipe แสดง Terrain ได้ไกลโดยไม่ต้องมี Height Raster ทั้งโลก และมีค่าเริ่มต้นด้านระยะการแสดงผล 8 km แต่ยังไม่เปิดเผย Terrain Chunk Layout, Quadtree, Clipmap หรือ Streaming Algorithms
2. Architecture: Recipe Terrain ประเมิน Ground Procedurally ส่วน Heightfield ใช้ Bounded Grid และสามารถขยาย Display ด้วย SetTerrainDisplayExtension ซึ่งไม่ได้ขยาย Collision
3. Source Evidence: weave_coding → terrain_generation, terrain_generation → Lane choice, render_profiles
4. API Contract: SetTerrainDisplayExtension(radiusM) ใช้ขยายระยะแสดงภาพใน Hybrid Terrain และ Rendering Profiles สามารถจำกัด Resolution/Quality ตาม Device
5. Working Example: เอกสารระบุว่า SpawnTerrainRecipe เป็นเส้นทางที่รองรับ Seamless Open Terrain โดยไม่จำเป็นต้องสร้าง Terrain Chunks เองผ่าน Weave Code
6. Execution Trace: Camera Position/Visible Region → Terrain Display Generation → Render Geometry ส่วน Chunk Scheduling ภายในยังไม่เปิดเผย
7. Limits & Failure Modes: Display Extension ไม่ได้ให้ Collision หรือ Grid Edits นอกพื้นที่ Heightfield และไม่ได้รับประกันว่าจะมองเห็นภูมิประเทศ 8 km โดยไม่มีข้อจำกัดของ Camera/Fog
8. Verification: Expected: Recipe Terrain มองเห็นต่อเนื่องถึงระยะที่กำหนด; Actual: Not Run สำหรับ LOD/Streaming Trace
9. Disclosure Status: Open Terrain Display Behavior Documented; Chunk/LOD Algorithms Undisclosed
10. Research Gaps: Chunk Size, LOD Error Metrics, Streaming Queue, GPU Upload, Cache Policies และ Memory Eviction
108 — รองรับการแก้ Terrain ระหว่างเล่นหรือไม่?
1. Direct Answer: รองรับโดยตรงสำหรับ Recipe Terrain ผ่าน TerrainDig() และ TerrainFlatten() โดยระบบใช้ Sparse Overlay เก็บการเปลี่ยนแปลง ไม่จำเป็นต้องสร้าง Base Terrain Recipe ใหม่ทั้งหมด
เอกสารยืนยันว่าการแก้ไขมีผลต่อ Collision, Rendering และ Ground Queries อีกทั้งรองรับ Multiplayer Synchronization และ Rollback ตามข้อกำหนดที่เผยแพร่
2. Architecture: Runtime Terrain Editing แยก Base Procedural Field ออกจาก Sparse Edit Overlay ซึ่งถูกสร้างเป็น Tiles เมื่อเกิดคำสั่งแก้ไข
3. Source Evidence: weave_coding → terrain_generation → Runtime digging; Built-in API Lookup ของ TerrainDig, TerrainFlatten, GetTerrainEditVersion และ TerrainOverlayClear
4. API Contract:
Radius, Depth และ Height ใช้หน่วยเซนติเมตร โดย TerrainDig() และ TerrainFlatten() คืนจำนวน Cells ที่เปลี่ยนแปลง
5. Working Example:
ตัวอย่างนี้แสดง API ที่มีเอกสารรองรับ แต่ต้องผูก Class กับ Object ที่รับ Input ได้ และมี Recipe Terrain อยู่ใน World จึงจะทำงานครบถ้วน
6. Execution Trace — Expected: Input E → TerrainDig → Update Sparse Overlay → Update Collision/Display/Queries → Increment Terrain Edit Version → Notify Terrain Edit Event
7. Limits & Failure Modes: Overlay มีขนาด Tile ละ 32×32 Cells และจำกัด 1,024 Tiles หาก Budget หมด การแก้ไขใหม่อาจไม่เกิดผลและคืน 0 การเรียก TerrainDig ทุก Frame โดยไม่จำเป็นอาจทำให้ Terrain Lag หรือ Flicker
8. Verification: Expected: Ground Height เปลี่ยนหลังการขุด และ Version เพิ่มขึ้น; Actual: Not Run สำหรับ Runtime Digging Test
9. Disclosure Status: Documented; Internal Overlay Storage/Replication Implementation Undisclosed
10. Research Gaps: Edit Propagation Latency, Overlay Compression, Collision Rebuild Cost, Persistence Round-trip, Multiplayer Conflict Resolution และ Maximum Edit Throughput

110 — Benchmark ของโลกขนาด 1, 4 และ 8 กิโลเมตร
1. Direct Answer: Oriverse มี Terrain Recipe ที่เหมาะสำหรับพื้นที่ขนาดกิโลเมตร และเอกสารระบุระยะการแสดง Terrain เริ่มต้น 8 km แต่ ยังไม่มีผล Benchmark ที่ยืนยันได้สำหรับพื้นที่ทดสอบ 1, 4 และ 8 km ภายใต้เงื่อนไข Hardware, Resolution และ Scene Complexity เดียวกัน
จึงไม่สามารถรายงาน FPS, Frame Time, CPU Memory หรือ VRAM ของแต่ละขนาดเป็นตัวเลขจริงได้ในรอบนี้
2. Architecture: ควร Benchmark ด้วย Recipe Terrain ชุดเดียวกัน โดยเปลี่ยนขอบเขตการสำรวจและระยะการแสดงผล ขณะควบคุม Terrain Features, Vegetation Density, Camera Height และ Rendering Quality
ต้องแยก World Extent ออกจาก Visible Distance: พื้นที่ทดสอบกว้าง 8 km ไม่ได้หมายความว่าต้องแสดง Terrain ทั้ง 8 km จากทุกตำแหน่งกล้อง
3. Source Evidence: terrain_generation, weave_coding → terrain_generation, render_profiles และสัญญาของเครื่องมือ sample_ground, preview_terrain, playtest
4. API Contract:
SpawnTerrainRecipe มีข้อกำหนดว่าหนึ่ง World ใช้ Recipe Terrain หลักได้หนึ่ง Instance ตามคู่มือ
