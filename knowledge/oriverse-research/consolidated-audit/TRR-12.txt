อย่างไรก็ตาม ยังไม่พบเอกสารเปิดเผยรายละเอียดภายในของ UI Layout Engine, Binding Dependency Graph, DOM Diffing Algorithm หรือ Event Dispatch Queue ครบถ้วน

111 — #html รองรับ HTML/CSS Subset ใดบ้าง?
1. Direct Answer: #html Name ... #end รองรับ HTML Tags และ CSS Properties ชุดจำกัดที่ Engine กำหนด ไม่รองรับ Browser DOM, JavaScript หรือ CSS ทั้งมาตรฐาน
2. Architecture: UI Definition อยู่ใน Weave Source เดียวกับ World/Classes โดย Canvas อ้าง html="Name" และ Binding อ่านค่า Controller Instance ที่ผูกกับ Canvas
3. Source Evidence: weave_coding → html_ui → Supported tags / CSS properties / Selectors
4. API Contract:

8. Verification: Expected: HTML/CSS ที่รองรับสร้าง UI ได้; Actual: ตัวอย่าง Official Guide มีหลักฐานรองรับ แต่ยังไม่ได้ Compile ตัวอย่างย่อแยกในรอบนี้

112 — screenCanvas และ worldCanvas แตกต่างกันอย่างไร?
1. Direct Answer: screenCanvas ใช้ Viewport เป็นพื้นที่ Layout สำหรับ HUD, Menus และ Modal Dialogs ส่วน worldCanvas ยึดกับ World Position แต่แสดงด้วยขนาด CSS Pixels ที่คงที่บนหน้าจอ
2. Architecture: ทั้งสองใช้ #html และ Controller Binding แบบเดียวกัน ต่างกันที่ระบบกำหนดตำแหน่งและ Viewport Reference
3. Source Evidence: weave_coding → html_ui, ui_patterns
4. API Contract:
worldCanvas ต้องมี size ซึ่งแต่ละแกนอยู่ในช่วง 1–8,192 CSS Pixels
5. Working Example:
6. Execution Trace: World Object Position → Camera Projection → Screen-space Placement → HTML Layout → Render
7. Limits & Failure Modes: worldCanvas ที่อยู่หลังกล้อง นอกจอ หรือ Hidden จะรับ Input ไม่ได้ World Canvas ไม่มี Depth Occlusion และจะแสดงใต้ Screen Canvases
8. Verification: Expected: World Canvas เคลื่อนตำแหน่งตามจุดยึดในโลก โดยขนาด CSS บนจอคงที่; Actual: Documented, ไม่ได้ตรวจ Camera Movement แยกในรอบนี้
9. Disclosure Status: Documented
10. Research Gaps: Projection Precision, Overlap Sorting, Occlusion Policy และ Screen-edge Clamping
113 — Data Binding จาก Class State ไป UI อัปเดตเมื่อใด?
1. Direct Answer: Oriverse รองรับ Typed Data Binding โดย HTML Elements อ่านค่า Fields จาก Controller และเมื่อ Gameplay State เปลี่ยน UI จะอัปเดตตามค่าใหม่
แต่เอกสารไม่ได้เปิดเผยว่าภายในใช้ Dirty Flags, Dependency Graph, Polling หรือ Batched Diffing และไม่ได้ระบุ Refresh Latency แบบ Guaranteed ในหน่วยมิลลิวินาที
2. Architecture: Weave Controller State → Typed Binding Paths → HTML Elements โดย Binding อาจอ้าง Class References ที่มีชนิดถูกต้อง
3. Source Evidence: html_ui → Typed paths / Update gameplay fields to update the view
4. API Contract:
Binding
	Data Type
	data-text
	Number / Text
	data-value, data-max
	Number
	data-show
	Bool
	data-enabled
	Bool
	data-class-NAME
	Bool
	data-src
	ImageAsset Object
	5. Working Example:
6. Execution Trace — Expected: Initial Money 20 → User Click Earn → UiAction → Money 25 → Bound Text Displays 25
7. Limits & Failure Modes: Bound Text ถูกแสดงเป็น Literal UTF-8 ไม่ตีความเป็น HTML ข้อมูล Dynamic Text ต่อ Viewer มีเพดาน 1 MiB และต่อ Node/Inline Flow 8 KiB
8. Verification: Expected: Text เปลี่ยนจาก 20 เป็น 25; Actual: คู่มือยืนยัน Binding Behavior แต่ Fixture นี้ยังไม่ได้รัน
9. Disclosure Status: Binding Contract Documented; Internal Update Mechanism Undisclosed
10. Research Gaps: Binding Latency, Change Detection, Batch Updates, Render Frame Synchronization และ Large-list Refresh Costs
114 — UiAction และ Event.Presser ส่งข้อมูลอย่างไร?
1. Direct Answer: เมื่อผู้เล่นกด Button ที่มี data-action="ActionName" ระบบเรียก event UiAction[ActionName] บน Controller ของ Canvas โดย Event.Presser ระบุ PlayerObject ที่เป็นผู้กระทำ
2. Architecture: UI Event → Canvas Controller → Handler → Permission/State Validation → Game State Mutation
3. Source Evidence: html_ui → UI actions; example_html_shop, example_html_inventory
4. API Contract:
สำหรับ Repeated Rows มี Event.Row; สำหรับ Inventory มี Event.Inventory, Event.Slot, Event.Item; สำหรับ Targeted Actions มี Event.Target
5. Working Example — จาก Official Inventory Pattern:
6. Execution Trace: Click Button → Resolve Action/Row/Slot → Populate Event Context → Execute Handler → Validate Current State → Apply Operation
7. Limits & Failure Modes: ห้ามเชื่อเพียงว่า Button ถูก Disable หรือซ่อนอยู่ ต้องตรวจสิทธิ์และสถานะจริงอีกครั้งใน Handler โดยเฉพาะ Price, Stock, Access และ Item Ownership
8. Verification: Expected: ผู้เล่นที่ไม่มีสิทธิ์ไม่สามารถทำ Inventory Operation ได้; Actual: Documented, ยังไม่ได้ทำ Negative Authorization Test
9. Disclosure Status: Event Context Documented; Internal Dispatch Implementation Undisclosed
10. Research Gaps: Event Ordering, Duplicate-click Handling, Replay Prevention, Rate Limiting และ Server Trust Boundary
115 — Inventory Template และ Drag & Drop ทำงานอย่างไร?
1. Direct Answer: Oriverse มี Native Inventory Container ที่สามารถแสดงผ่าน template data-inventory="Bag" โดย UI สร้าง Slot Rows จากข้อมูล Inventory จริง ไม่ต้องเขียน Slot Widgets เองทีละช่อง ระบบรองรับการลากเพื่อสลับหรือรวม Stack และส่ง Events ที่เกี่ยวข้องกับการลาก/วาง
2. Architecture: Inventory Handle → data-inventory → Slot Elements → Pointer Drag/Drop → Inventory Operation/Event Handler → Inventory State Update → UI Refresh
3. Source Evidence: weave_coding → inventory, html_ui, example_html_inventory; สัญญาเครื่องมือ playtest → drag
4. API Contract:
CreateInventory จำกัด 1–128 Slots โดย Inventory Handle เป็น Object Handle ที่ไม่ใช่ Scene Object ส่วน MoveSlot รองรับการ Swap และการ Merge Stack โดยอาจย้ายได้เพียงบางส่วนเมื่อปลายทางเต็ม
5. Working Example — จาก Official Inventory Guide:
ตัวอย่างย่อนี้ต้องมี item apple, item pear และ Canvas Declaration เพิ่มเติมจึงจะใช้งานเป็น World สมบูรณ์
6. Execution Trace — Expected: Inventory Spawn → Create 12 Slots → Add Apples/Pears → Render Slots → User Selects/Drags → Engine Emits Action/Drop → Controller Validates → Update Inventory
7. Limits & Failure Modes: Drag ต้องเริ่มบน Draggable Slot จริง หากมี UI Layer ที่ pointer-events:auto ทับอยู่ อาจทำให้ Input ไม่ถึง Slot และการย้ายข้าม Inventory ต้องตรวจ Owner/Permission ใน Gameplay Logic
8. Verification: Expected: Slot Selection ถูกต้อง และการ Drag/Drop สามารถ Swap/Merge Items ได้; Actual: Not Run สำหรับ Drag/Drop Test ในรอบนี้
9. Disclosure Status: Inventory Binding/Operations Documented; UI Drag/Drop Internals Undisclosed; Runtime Behavior Not Verified
10. Research Gaps: Drag Event Ordering, Concurrent Inventory Mutation, Multi-touch Drag, Transaction Atomicity และ Drag Preview Rendering
116 — UI Ownership และ Visibility สำหรับ Multiplayer
1. Direct Answer: screenCanvas ที่ประกาศใน Scene โดยตรงแสดงต่อผู้เล่นทุกคนเป็นค่าเริ่มต้น ส่วน UI เฉพาะผู้เล่นใช้ SpawnCanvas() แล้วกำหนด SetPlayerOwnerIndex(GetPlayerIndex())
2. Architecture: Gameplay Simulation ยังคงเป็น Shared Deterministic State แต่ระบบ Rendering/Hit-testing เลือกแสดง Canvas ตาม Owner ของ Viewer
3. Source Evidence: multiplayer_guidance → Per-player UI, html_ui, example_html_inventory
4. API Contract:
การใช้ SetPlayerOwnerIndex(-1) ทำให้ Canvas กลับมาเป็น Public UI
5. Working Example — จาก Official Inventory Guide:
6. Execution Trace: Player A Joins → Spawn Canvas A → Set Owner A → Player B Joins → Spawn Canvas B → Set Owner B → Each Viewer Sees/Clicks Only Owned Canvas
7. Limits & Failure Modes: UI Visibility ไม่ใช่ Data Security Boundary เพราะ Gameplay State ยังถูกจำลองร่วมกัน การซ่อน Canvas จาก Player B ไม่ได้ทำให้ข้อมูลใน Shared Simulation เป็นความลับ
8. Verification: Expected: Player A ไม่เห็นหรือกด Canvas B; Actual: Documented, ยังไม่ได้รัน Multi-seat UI Inspection ในรอบนี้
9. Disclosure Status: UI Ownership Documented; Security Isolation Unsupported หากอ้างจาก Visibility เพียงอย่างเดียว
10. Research Gaps: Owner Change Timing, Input Routing Under Rollback, Shared Canvas Access Control และ UI Security Test Matrix
117 — Responsive Layout และ Mobile Touch
1. Direct Answer: Oriverse รองรับ Responsive Layout ผ่าน CSS Flex/Grid, Percentages, Viewport Units และ @media (min-width/max-width) รวมถึง Mobile Touch Buttons ที่เชื่อมกับ Shared Actions
2. Architecture: UI Layout ปรับตาม Canvas Viewport ขณะที่ Gameplay Input สามารถใช้ Action Abstraction เดียวกันระหว่าง Desktop Keyboard/Mouse และ Mobile Touch
3. Source Evidence: html_ui → CSS / Responsive; inputs → Shared Actions / Mobile
4. API Contract: รองรับ px, %, em, rem, vw, vh, vmin, vmax, fr, minmax() และ repeat() สำหรับ Grid
Custom Action:
รองรับ Custom Actions สูงสุด 27 รายการต่อ World
5. Working Example:
6. Execution Trace — Expected: Desktop 420px Canvas → 3 Columns; Narrow 320px Viewport → 2 Columns; Mobile Action Button → Shared Gameplay Action
7. Limits & Failure Modes: Custom Actions ที่ Binding Keys ซ้ำกันทำให้ Load Error และ Raw Keyboard Events ไม่ทำงานบน Mobile/Bots เทียบเท่ากับ Shared Actions
8. Verification: Expected: Layout ยุบเป็น 2 Columns เมื่อ Viewport แคบ และ Mobile Touch ส่ง Action เดียวกับ Desktop; Actual: Not Run สำหรับ Responsive/Mobile Matrix
9. Disclosure Status: Documented; Cross-device Visual Results Not Verified
10. Research Gaps: DPI Scaling, Safe-area Behavior บนอุปกรณ์จริง, Touch Hit Target Accuracy, IME Input และ Accessibility Support
118 — Focus, Keyboard Capture และ Modal Dialog
1. Direct Answer: UI รองรับ Local Modal Dialog ผ่าน HTML <dialog> พร้อม commandfor และ command="show-modal"/"close" เมื่อ Modal เปิด ระบบจับ Input และปล่อย Held World Controls ส่วน Escape/Close คืน Focus ตามที่คู่มือกำหนด
2. Architecture: Dialog State, Focus และ Scroll เป็น Viewer-local UI State ไม่ใช่ Shared Gameplay State
3. Source Evidence: html_ui → Local menus; example_html_menu; inputs
4. API Contract:
และ SetCursorUiMode(true) ใช้ปล่อย Mouse-look พร้อมแสดง Cursor
5. Working Example — จาก Official Menu Example:
6. Execution Trace: Click Help → Show Modal → Capture Input/Release Held World Controls → User Presses Escape or Close → Restore Focus
7. Limits & Failure Modes: pointer-events:none ทำให้ UI Wrapper ส่ง Mouse/Touch ผ่านได้ แต่ไม่ควรตีความว่าเป็นการปิด Keyboard Focus และ Canvas ที่ซ้อนทับอาจ Block World Input หากตั้ง Pointer Events ไม่เหมาะสม
8. Verification: Expected: เปิด Modal แล้วไม่ทำให้ Player Movement ค้าง และ Escape ปิด Modal ได้; Actual: Not Run
9. Disclosure Status: Modal/Focus Semantics Documented; Internal Focus Manager Undisclosed
10. Research Gaps: Nested Modal Priority, Gamepad Focus, IME Edge Cases, Focus Restoration Under Canvas Destroy และ Accessibility Navigation

Oriverse มี HTML/CSS Subset ที่ผูกกับ Weave Controller Fields ได้ รองรับ screenCanvas, worldCanvas, UiAction, Repeated Lists, Native Inventory, Modal Dialogs และ Responsive Layout
ระบบรองรับ Canvas Ownership สำหรับ Multiplayer โดย Viewer เห็นและกดเฉพาะ UI ของตนเองได้ แต่ UI Visibility ไม่ใช่ Security Boundary ของ Shared Simulation
ข้อจำกัดที่สำคัญ ได้แก่ 128 Retained Canvases ต่อ Viewer, 512 Source Nodes ต่อ Canvas และ 1,024 Expanded Nodes ต่อ Canvas
สิ่งที่ยังไม่เปิดเผย
Internal DOM/Layout Representation, Binding Diff Algorithm, Frame-level UI Refresh Contract, Input Dispatch Internals, Drag/Drop Atomicity, UI Render Batching และ Performance Cost ต่อ Canvas/Node
ข้อเสนอทางวิศวกรรมสำหรับ KHOSAN Studio

ควรแยก UI Presentation ออกจาก Gameplay Authorization เสมอ โดยเฉพาะ Shop, Inventory และ Multiplayer Economy และกำหนดชุดทดสอบอัตโนมัติที่ครอบคลุม Responsive Layout, Drag & Drop, Input Focus, Duplicate Actions และ Cross-player UI Isolation
