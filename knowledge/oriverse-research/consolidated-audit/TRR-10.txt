091 — #texture สร้าง PBR Maps ด้วยขั้นตอนใด?
1. Direct Answer: #texture เป็น Procedural Material DSL ที่ประเมิน Expression Graph และ Bake เป็น Texture Maps บน CPU เมื่อโหลด Asset ไม่ได้รัน Expression Graph ทุก Frame
ผลลัพธ์หลักประกอบด้วย Albedo/Color, Normal และ ORM ซึ่งหมายถึง Ambient Occlusion, Roughness และ Metalness พร้อมข้อมูล Alpha หรือ Emission ตามเงื่อนไข
2. Architecture:
ผังระดับหน้าที่จากคู่มือ ไม่ใช่ Internal Render Graph
3. Source Evidence: texture_dsl → Core syntax / Outputs; texture_dsl_usage
4. API Contract: out.color เป็น vec3; out.normal เป็น Normal Vector; out.orm บรรจุ AO, Roughness, Metalness; out.alpha และ out.height เป็น Scalars โดย out.emission และ out.height ใช้ร่วมกันไม่ได้ในช่องที่กำหนดไว้
5. Working Example — ผ่าน Texture Inspector จริง:
6. Execution Trace: Parse Texture DSL → Evaluate Noise → Calculate Colors → Derive Normals → Pack ORM → Bake 128×128 Texture Maps
7. Limits & Failure Modes: การเพิ่ม Resolution เป็นสองเท่าทำให้จำนวน Texels เพิ่ม 4 เท่า และการเว้น out.normal/out.orm อาจเกิด Warning พร้อมใช้ Default Maps
8. Verification: Expected: Color, Normal, Roughness และ Metallic มีข้อมูลถูกต้อง Actual: PASS — Roughness มีค่า 0.85 ทุก Sample, Metallic เท่ากับ 0, 16,384 Texels ต่อ Channel และไม่มี Nonfinite Values
9. Disclosure Status: Documented + Experimentally Verified
10. Research Gaps: Internal Texture Encoding, Compression, Mipmap Generation, Cache Invalidation และ GPU Residency

2. Architecture: ระบบใช้ค่า uv และ Procedural Parameters เป็น Inputs แล้วคำนวณ Material Channels ผ่าน Expressions
3. Source Evidence: texture_dsl → Built-ins

6. Execution Trace: Sample UV → Evaluate Noise → Blend Color → Output Channels
7. Limits & Failure Modes: Texture DSL ไม่มี General-purpose Conditionals; ใช้ Masks และ Math แทน ส่วน for Loops ถูกจำกัดจำนวนครั้งในการ Unroll

9. Disclosure Status: Documented / Partially Experimentally Verified
10. Research Gaps: Procedural Graph Optimization, Noise Kernel Internals, GPU Bake Support และ Node-level Profiling

094 — #shader เชื่อม WGSL เข้ากับ Material Pipeline อย่างไร?
1. Direct Answer: #shader ใช้ Raw WGSL ที่ถูกผนวกเข้ากับ Standard Lit Material ของ Engine โดยผู้เขียนสามารถปรับ Vertex Positions และ Surface Outputs ได้ ขณะที่ Lighting, Shadows, IBL, Fog, Cutout, LOD และ Motion Vectors ยังคงอยู่ภายใต้ความรับผิดชอบของ Engine
2. Architecture: Shader แบ่งได้เป็น @module Helpers, @vertex Stage และ Fragment Body
3. Source Evidence: shader_dsl → Structure
4. API Contract: Vertex Stage ใช้ ctx.world_pos, ctx.normal, ctx.uv; Fragment Stage เขียน out.base_color, out.world_normal, out.orm และ out.emissive ตามชนิด Material
5. Working Example — จากคู่มือ:
6. Execution Trace: World Material → WGSL Injection → Vertex Deformation → Fragment Material Outputs → Engine Lighting/Postprocessing
7. Limits & Failure Modes: Shader Compile ผิดแล้ว Material อาจกลับไปใช้ Default และ Browser WGSL Validator มีข้อจำกัดเข้มงวดกว่า Desktop ในบางกรณี
8. Verification: Expected: Vertex Sway และ Color Gradient ทำงาน; Actual: Documented Example, ยังไม่ได้ Compile/Render Shader นี้ในรอบนี้
9. Disclosure Status: Public Shader Hooks Documented; Internal Pipeline Assembly Undisclosed
10. Research Gaps: Shader Compilation Pipeline, Pipeline Cache, Bind Group Layout และ Render-pass Integration
095 — Rendering Pipeline เป็น Forward, Deferred หรือ Hybrid?
1. Direct Answer: เอกสารและเครื่องมือ Oriverse แสดงหลักฐานว่า Engine มีทั้ง Deferred Rendering Path และ Forward/Transparent Path จึงกล่าวได้ว่ามีการใช้หลาย Rendering Paths แต่ยังไม่สามารถยืนยัน Internal Render Graph ทั้งหมดหรือจัดประเภทว่าเป็น Hybrid แบบใดอย่างเป็นทางการ
2. Architecture: Deferred Path รองรับการตรวจ Material และ Lighting Components ผ่าน AOV Diagnostics ส่วน Water, Particles และ Forward/Transparent Materials มีเส้นทาง Render ที่ต่างออกไป
3. Source Evidence: Tool Contract ของ playtest → debug_view/debug_views และ shader_dsl
4. API Contract: playtest รองรับการเลือก debug_view เช่น albedo, normal, ao, roughness, metallic, direct, ambient, shadow และ local_lights
5. Working Example: การเลือก debug_views: ["albedo", "normal", "roughness", "metallic"] เป็น Configuration สำหรับตรวจ Material Passes โดยไม่ต้องเขียน Shader ใหม่
6. Execution Trace: Geometry/Material Processing → Lighting Evaluation → Transparent/Forward Rendering → Post-processing เป็นแผนภาพเชิงแนวคิด ไม่ใช่ลำดับ Pass จริงทุกขั้น
7. Limits & Failure Modes: AOV Capture ข้าม Enhanced Lighting บางส่วนและใช้ Fast-path Lighting จึงไม่เหมาะสำหรับวัดคุณภาพ Lighting ขั้นสุดท้ายทุกระบบ
8. Verification: Expected: AOV Views แสดงข้อมูลของ Deferred Path; Actual: เครื่องมือรองรับตามสัญญา แต่ยังไม่ได้รัน AOV Capture ในรอบนี้
9. Disclosure Status: Deferred/Forward Paths Documented; Full Renderer Architecture Undisclosed
10. Research Gaps: G-buffer Layout, Render Pass Ordering, Depth Prepass, Light Culling, Render Graph Scheduling และ Transparency Composition

098 — Runtime Material Parameters เปลี่ยนได้เพียงใด?
1. Direct Answer: Oriverse เปิดให้เปลี่ยน Material Parameters ผ่าน Weave Runtime โดยรองรับ 32 Scalar Parameters ต่อ Material และ Texture Parameter Slots ตาม Shader Contract
2. Architecture: Material มี Runtime Parameter Storage ที่ WGSL Shader อ่านผ่าน mat.params4 ขณะที่ Weave Script ใช้ Built-in APIs เปลี่ยนค่า
3. Source Evidence: shader_dsl → Runtime control; Built-in Functions SetMaterialParameterNumber, SetMaterialParameterTexture, SetAssetSubmeshMaterial
4. API Contract:
หมายเหตุ: คู่มือ Shader กล่าวถึง 16 Texture Slots (tex0..tex15) แต่รายการ Built-in Function ระบุช่วง Slot 0..16 ซึ่งอาจนับไม่ตรงกัน จึงต้องยืนยันขอบเขต Slot สูงสุดจาก Runtime ก่อนใช้งานจริง
5. Working Example:
ใน Shader ใช้ mat.params4[0].x อ่านค่าจาก Slot 0
6. Execution Trace: Gameplay Event → Set Material Parameter → Shader Reads Parameter → Render Output Changes
7. Limits & Failure Modes: Parameter Slots มีขอบเขตจำกัด และ Shader แต่ละตัวกำหนดความหมายของ Slot เอง ต้องอ่าน WGSL ก่อนเปลี่ยนค่า นอกจากนี้ Particle/Water Shader บางประเภทไม่รองรับ Texture Parameter Slots
8. Verification: Expected: การเปลี่ยน Parameter ทำให้ Film Grain Intensity เปลี่ยน; Actual: Not Run
9. Disclosure Status: Runtime Parameter Contract Documented; Slot-16 Boundary Not Verified
10. Research Gaps: Material Instance Isolation, Parameter Update Cost, GPU Uniform Buffer Layout และ Concurrent Material Mutations
099 — WebGPU และ Graphics Fallback แตกต่างกันอย่างไร?
1. Direct Answer: Oriverse รองรับ Rendering บน Web และ Desktop แต่เอกสารที่ตรวจสอบยังไม่เปิดเผย Graphics Backend Matrix ครบทุกแพลตฟอร์ม เช่น WebGPU, WebGL, Vulkan, Metal หรือ DirectX ที่ใช้งานจริงในแต่ละอุปกรณ์
อย่างไรก็ตาม คู่มือระบุว่า Browser WGSL Validation เข้มงวดกว่า Desktop ในบางกรณี และมีระบบ Adaptive Render Quality สำหรับอุปกรณ์ที่ประสิทธิภาพแตกต่างกัน
2. Architecture: World Rendering Settings สามารถถูกปรับตาม Client Capabilities, Device Limits และ Local Quality Preferences
3. Source Evidence: shader_dsl → Caveats; render_settings; render_profiles
4. API Contract:
และ:
5. Working Example: ตัวอย่าง Render Profile ข้างต้นเป็น Syntax จากคู่มือ ใช้กำหนดเป้าหมาย Rendering สำหรับ Mobile
6. Execution Trace — Expected: Detect Device → Apply World Render Profile → Respect Device Limits/Local Overrides → Adapt Quality Under Sustained Load
7. Limits & Failure Modes: การกำหนด target_fps = 60 ไม่ได้การันตีว่าอุปกรณ์ทุกเครื่องจะได้ 60 FPS และ fallback_fps มีผลต่อ Rendering Target ไม่ใช่ Simulation Tick Rate
8. Verification: Expected: Mobile ใช้ Rendering Resolution และ Texture Caps ตาม Profile เมื่ออยู่ภายใต้ข้อกำหนดอุปกรณ์; Actual: Not Run สำหรับ Cross-platform Benchmark
9. Disclosure Status: Adaptive Quality Policy Documented; Complete Graphics Backend/Fallback Matrix Undisclosed
10. Research Gaps: WebGPU Adapter Requirements, Browser Feature Detection, WebGL Fallback Availability, Shader Compatibility และ Device-specific Performance
